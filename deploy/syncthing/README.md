# Изолированный стенд A1

Два переносимых экземпляра **Syncthing v2.1.7**, без Docker. Требуется Python
3.12; команды выполняются из корня репозитория в окружении с этой версией.
Сценарии самого стенда используют стандартную библиотеку Python. Рабочий
адаптер A1.2–A1.4 реализован в `backend/app/syncthing_adapter/`; для его проверки
требуется подготовленное backend-окружение Python 3.12 с зависимостями A0.
Подключение к A2/A3/B2 и пределы адаптера описаны в
[передаче A1.5](../../backend/app/syncthing_adapter/README.md); итоговые результаты
и точные JSON-доказательства — в
[сводке приёмки](../../tests/integration/syncthing_adapter/acceptance-a1.json).

## Повторить A1.1

```text
python deploy/syncthing/bench.py verify --export-fixtures
```

При первом запуске загружается архив из официального релиза, выбранный в
[release.json](release.json). SHA-256 проверяется до извлечения единственного
исполняемого файла и перед каждым запуском. Повреждённый кеш требует повторной
подготовки; непроверенный бинарник не запускается. Бюджет загрузки — 300 секунд,
таймаут сетевого чтения — 30 секунд. Следующие запуски используют проверенный кеш.

`verify` проверяет свободные порты, создаёт собственные home, запускает узлы
без видимых окон и ожидает готовности API. Затем проверяет настройки изоляции,
записывает один демонстрационный файл, отправляет `POST /rest/db/scan` и ожидает
точного совпадения байтов на втором узле. Готовность ограничена 25 секундами,
ожидание передачи — 35 секундами; HTTP-запросы ограничены 5 секундами.
Оба процесса останавливаются в `finally`.

Стенд владеет непосредственно рабочим процессом каждого узла. Для закреплённой
версии 2.1.7 только при `serve` явно устанавливается `STMONITORED=yes`:
обычный `--no-restart` оставляет отдельный monitor и дочерний worker. Завершение
одного monitor при недоступном shutdown API могло оставить worker и блокировку
home. Внутренний режим выбран по
[исходникам закреплённой версии](https://github.com/syncthing/syncthing/blob/v2.1.7/cmd/syncthing/main.go#L283-L286);
при обновлении версии его нужно перепроверить. CLI-пробы используют очищенное
окружение без этого значения; чужие `ST*` переменные по-прежнему удаляются.

Флаг `--export-fixtures` явно разрешает обновить:

- [18 сокращённых ответов и manifest](../../tests/contract/syncthing_adapter/fixtures/v2.1.7/manifest.json).
- [Отчёт реального запуска](../../tests/integration/syncthing_adapter/evidence-v2.1.7.json).

Без флага отчёт сохраняется только в игнорируемом `runtime/verification.json`.
Стенд проверен на Windows amd64; путь для Linux amd64 подготовлен, но не испытан.

## Ручное управление стендом

```text
python deploy/syncthing/bench.py prepare
python deploy/syncthing/bench.py start
python deploy/syncthing/bench.py status
python deploy/syncthing/bench.py capture
python deploy/syncthing/bench.py stop
```

`prepare` только получает и проверяет бинарник. `start` восстанавливает исходную
конфигурацию двух принадлежащих стенду home перед запуском; остановленный стенд
не предназначен для хранения ручных изменений конфигурации. `capture` выполняет
чтения на уже запущенных узлах; сохранение fixtures требует того же явного флага.
`verify` требует предварительно остановить стенд и сам управляет его жизненным циклом.

| Узел | API HTTP | Синхронизация TCP |
|---|---|---|
| node-a | 127.0.0.1:18384 | 127.0.0.1:22101 |
| node-b | 127.0.0.1:28384 | 127.0.0.1:22102 |

Каждый узел имеет две папки: `scc-a1-shared` для передачи файла и
`scc-a1-control` для будущего контроля побочных изменений. У обеих
`rescanIntervalS=7200`, `fsWatcherEnabled=false`, исходный `paused=false`.
Global/local discovery, relay, NAT, автообновление и телеметрия отключены;
адрес второго узла задан явно. API-ключи, сертификаты, XML, данные, архивы,
PID и журналы остаются внутри игнорируемого `deploy/syncthing/runtime/`.

Сценарий отказывается использовать непомеченный существующий home или занятый
порт. Остановка проверяет PID, время создания и путь бинарника внутри runtime,
поэтому повторное использование PID не даёт права завершить чужой процесс.
HTTP-клиент принимает только фиксированные адреса стенда и запрещает redirects.
Клиент A1.1 не позволяет отправить PATCH. Начальная конфигурация задаётся
офлайн в принадлежащих стенду XML. Device ID получается из сертификата через
CLI device-id и не зависит от порядка сохранённых устройств в XML.

## Проверить рабочий адаптер, события и pause/resume

```text
python tests/integration/syncthing_adapter/check_live.py --export-evidence
```

Команда сама запускает и останавливает стенд; заранее запущенный стенд нужно
остановить. Этот отдельный сценарий отправляет PATCH через рабочий адаптер
только для демонстрационной папки node-a. Он сравнивает полный объект конфигурации
с исходным, проверяет контрольную папку и обе конфигурации node-b, наблюдает
паузу, затем возобновляет и проверяет передачу файла с node-b на node-a.
Отдельно проверяются чтения, реальные события, пустой long poll, неверный ключ,
404 чтения/записи, явный перезапуск процессов и недоступность после остановки.

Результат сохраняется в игнорируемом `runtime/adapter-verification.json`;
`--export-evidence` дополнительно обновляет
[обезличенный отчёт](../../tests/integration/syncthing_adapter/evidence-adapter-v2.1.7.json).
HTTP-ответ PATCH, paused, runtime, restart-required и сессия записываются
раздельно. Отчёт не присваивает статус Execution и не заменяет человеческую
проверку конфигурации перед merge.

На проверенной версии paused-папка возвращает пустой runtime state; адаптер
выдаёт invalid_response для этого наблюдения, сохраняя возможность отдельно
читать её конфигурацию. Непрерывность событий проверяется по
[D-01, редакции 2](../../docs/design/a/d01-stream-continuity.md): сохранённый
ориентир должен совпасть с событием текущего окна. При потере доказательства
создаётся новая эпоха и требуется since=0, даже если startTime совпал.

## Проверить D-01 и восстановление backend

```text
python tests/integration/syncthing_adapter/check_d01.py
```

Сценарий повторяет pause/resume выше, затем сериализует checkpoint и проверяет
его восстановление отдельным процессом Python без перезапуска Syncthing.
После настоящего рестарта источника тестовый транспорт удерживает startTime
и uptime прежними; реальные события нового потока уже обгоняют старый курсор.
Проверяются отказ принять старый курсор, новая эпоха и чтение с события 1.
Это управляемая симуляция совпавших status-полей на реальных событиях;
нативный перезапуск в одну секунду не заявляется.

Отчёт сохраняется в игнорируемом runtime/d01-verification.json и в
[обезличенном доказательстве](../../tests/integration/syncthing_adapter/evidence-d01-v2.1.7.json).
Оба собственных процесса останавливаются в finally. После собственной остановки
повторный запуск ограниченно ждёт освобождения четырёх портов Windows;
занятый чужим слушателем порт не переиспользуется, чужие процессы не завершаются.
Первый запуск по-прежнему сразу отказывается от занятого порта.

## Что установлено реальными запросами

- Семь успешных чтений на узел: status, version, folders, folder config,
  folder runtime, restart-required, events. Схемы сокращены по разрешённым
  полям; исходные значения id, startTime, времени событий и числовых полей
  сохранены. Пути заменены на `/DEMO`, произвольный payload событий удалён.
  Device ID принадлежат только двум свежим демонстрационным экземплярам.
- Неверный ключ даёт **403**, `text/plain`, `CSRF Error`; отсутствующая папка —
  **404**, `text/plain`. Классификация ошибок не должна требовать JSON-тела.
- Restart-required возвращает `{"requiresRestart": false}`. События используют
  `id` и `globalID`; дробная часть времени событий сохранена без нормализации.
- `startTime` имеет точность до секунды. В
  [исходном коде v2.1.7](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/ur/usage_report.go)
  время обрезается через `Truncate(time.Second)`, а
  [system/status](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/api/api.go)
  возвращает это значение. Следовательно, helper A0, использующий UUID узла и
  raw startTime, может дать одинаковую сессию для двух запусков в ту же секунду.
  Это вывод из исходного кода; такой быстрый рестарт отдельно не воспроизводился.
  Редакция 2 D-01 заменяет этот helper проверяемой непрерывностью. Для MVP
  дополнительный сервис boot UUID не требуется; потеря доказательства явно
  отделяет эпохи, не объявляя любой разрыв доказанным рестартом.

[плане API](../../docs/design/a/syncthing-api.md) и
[журнале A1](../../docs/agent-log/a/A1.md).
