# Курсовой проект: централизованное управление и контроль синхронизации файлов на базе Syncthing

> **Статус документа:** рабочее описание проекта и рекомендуемый план MVP, а не утверждённое преподавателем техническое задание.  
> **Команда:** два студента направления «Прикладная информатика».  
> **Главный приоритет:** законченная курсовая с самостоятельно разработанными модулями, рабочей демонстрацией, БД, тестированием и развёртыванием.  
> **Не является целью:** создание своего протокола передачи файлов, облачного файлового хранилища или полноценного аналога Syncthing.

## 1. Суть проекта простыми словами

Syncthing синхронизирует папки между компьютерами: следит за изменениями и передаёт файлы напрямую между доверенными устройствами. Но при работе с несколькими устройствами администратору может быть неудобно отдельно проверять состояние каждого экземпляра, вручную менять настройки и восстанавливать картину прошедших проблем.

**Предлагается разработать собственную систему управления поверх Syncthing.** Пользователь открывает единую веб-панель, видит управляемые устройства и папки, задаёт правила автоматизации и просматривает историю выполнения этих правил и возникающих проблем. Центральный сервер хранит **служебную информацию**, но **не передаёт и не хранит содержимое синхронизируемых файлов**.

**Типовой пример.** Есть рабочий ПК и небольшой сервер. Пользователь хочет видеть, доступен ли второй компьютер, актуальна ли общая папка и возникали ли ошибки. Он также хочет ограничить синхронизацию определённой папки выбранными временными интервалами. Система хранит такое правило, применяет его в Syncthing, проверяет результат и сообщает об отклонениях.

### В чём собственная работа команды

Не дублирование штатных кнопок Syncthing, а разработка **бизнес-логики управления и контроля**: общей модели устройств, правил и их выполнения, обработки отказов, накопления истории, API и интерфейса. Отдельный акцент — проверять **фактическое состояние**, а не считать команду успешной только потому, что HTTP-запрос получил ответ `200`.

## 2. Цель, задачи и границы

**Цель курсовой:** разработать и испытать клиент-серверную информационную систему для централизованного наблюдения за несколькими экземплярами Syncthing, автоматизированного управления синхронизацией и анализа истории её работы.

**Задачи:**

1. Изучить возможности Syncthing, REST API и существующего интерфейса; обозначить функционал своей надстройки.
2. Спроектировать модули, REST API, модель данных и сценарии отказов.
3. Реализовать подключение управляемых экземпляров и получение информации об устройствах/папках.
4. Реализовать правила управления синхронизацией и механизм проверки их выполнения.
5. Сохранять события, результаты команд и периодические наблюдения в БД.
6. Реализовать веб-интерфейс и минимальную аналитику по истории.
7. Подготовить воспроизводимое тестовое окружение, включая два экземпляра Syncthing.
8. Организовать agentic development, автоматическую валидацию кода и интеграционные тесты.
9. Развернуть серверную часть на VPS, продемонстрировать работу и оформить отчёт.

**Границы:** проект управляет конфигурацией и собирает метаданные Syncthing; он не реализует алгоритмы обмена файлами, не отвечает за исправление файловых конфликтов, не выполняет резервное копирование и не обещает гарантированную доставку к заданному времени.

## 3. Объём MVP: обязательное и необязательное

### 3.1. Обязательные сценарии

| ID | Возможность | Минимальный проверяемый результат |
|---|---|---|
| F-01 | Добавление управляемого экземпляра | Экземпляр появляется в системе; проверено подключение к его API через доверенный канал. |
| F-02 | Просмотр устройств/папок | Панель отображает настроенные папки и доступное состояние, полученное из Syncthing. |
| F-03 | Индикация проблем | «Узел недоступен», «папка приостановлена», «обнаружена ошибка» не смешиваются в один статус. |
| F-04 | Правила по времени | Пользователь задаёт допустимые дни/интервалы синхронизации для конкретной пары «экземпляр—папка». |
| F-05 | Применение правила | Планировщик меняет желаемое состояние папки (`paused`), затем сверяет его с фактическим. |
| F-06 | Работа после отключения | При возвращении узла система повторно определяет актуальное желаемое состояние и пытается его применить. |
| F-07 | История | Сохраняются значимые события и результаты попыток применения команд. |
| F-08 | Базовая аналитика | Есть хотя бы 2–3 рассчитываемых показателя и график/таблица за период. |
| F-09 | Администрирование | Вход в панель ограничен авторизованным пользователем (для MVP допустим один администратор). |
| F-10 | Проверка и развёртывание | Автоматические тесты, Docker Compose, работающая демонстрация на VPS и исходный код в репозитории. |

**Практичная граница:** два тестовых экземпляра Syncthing, одна–две папки, один администратор, одна временная зона на уровне правила, один режим правила «разрешать синхронизацию в заданные окна». Этого уже достаточно для полноценной курсовой.

### 3.2. Что сознательно оставляем за рамками MVP

- Массовое администрирование десятков независимых узлов.
- Автоматическое разрешение конфликтов версий файлов.
- Облачное хранение и пересылка файлов через центральный сервер.
- Полный редактор всех настроек Syncthing.
- Сложные роли, SSO, мультиарендность и публичная регистрация.
- Machine Learning, «умные» рекомендации, предсказание сбоев.
- Мобильное приложение, Telegram-уведомления и формирование PDF-отчётов.
- Динамическое ограничение скорости, если оно усложнит стабильность MVP.

**Правило управления объёмом:** сначала закончить цепочку «обнаружили состояние → применили правило → проверили → сохранили результат → показали в панели». Всё остальное — после неё.

## 4. Предлагаемая архитектура

```text
                           Пользователь
                                |
                         HTTPS + логин
                                v
                          Веб-интерфейс
                                |
                          REST API / JSON
                                v
                 +-----------------------------+
                 |    Backend на Python        |
                 |    FastAPI                  |
                 |  - учёт узлов и папок       |
                 |  - правила                  |
                 |  - журнал и статистика     |
                 +----+-----------+------------+
                      |           |
                      v           v
                 PostgreSQL   Scheduler / worker
                                  |
                           Адаптер Syncthing
                                  |
                        Доверенный канал / LAN
                            /             \
                           v               v
                      Syncthing A     Syncthing B
                           \______________/
                          передача файлов P2P
```

**Принципиальное различие:** центральный сервер не становится посредником файловой передачи; он передаёт только команды и метаданные. Синхронизация остаётся задачей Syncthing.

### 4.1. Рекомендуемое упрощение на время курсовой

Вместо немедленной разработки безопасной распределённой инфраструктуры:

- **Этап MVP:** два экземпляра Syncthing в изолированном Docker-окружении; backend обращается к их REST API по внутренней сети контейнеров. Эту конфигурацию легко воспроизвести на ноутбуке и VPS.
- **Если остаётся время:** демонстрация удалённого управляемого компьютера через VPN либо небольшой локальный helper/agent с **исходящим** соединением к серверу. Это отдельная интеграционная задача, не обязательное условие завершения MVP.

Такой подход **не означает**, что с MVP уже можно безопасно управлять произвольными компьютерами из интернета. Удалённая архитектура потребует самостоятельной проработки аутентификации и доставки команд.

### 4.2. Где лучше размещать компоненты

- **VPS:** веб-интерфейс, FastAPI, PostgreSQL, планировщик; для демонстрации — изолированные тестовые узлы Syncthing.
- **Рабочая локальная машина разработчика:** такое же тестовое окружение через Docker Compose.
- **Реальные компьютеры пользователя:** расширение после MVP, при условии защищённого доступа к локальному API.

## 5. Основные модули и ответственность

**1. Syncthing Adapter.** Изолирует обращение к внешнему API: чтение конфигурации, состояния узлов/папок, обновление параметра приостановки, получение событий. Другие модули не должны напрямую разбирать произвольные ответы Syncthing.

**2. Device & Folder Registry.** Хранит логическую регистрацию управляемых экземпляров, сопоставляет локальные ID папок, показывает текущие состояния. Важно: ID управляемого экземпляра в вашей БД и Syncthing Device ID — разные понятия; их нельзя автоматически считать взаимозаменяемыми.

**3. Rule Engine / Scheduler.** На основании текущего времени и активных правил рассчитывает **желаемое** состояние. Сам по себе не передаёт файлы.

**4. Reconciliation Worker.** Сравнивает желаемое и наблюдаемое состояние; при расхождении отправляет команду, затем проверяет, применена ли она. Пишет результат и возможную ошибку.

**5. Event & Snapshot Collector.** Сохраняет поток событий и периодические снимки состояния, умеет повторно опросить узел после сбоя соединения.

**6. Analytics.** Строит показатели по сохранённым событиям и наблюдениям. Не выдаёт недоступность мониторинга за подтверждённую недоступность Syncthing.

**7. Web UI.** Даёт обзор узлов, папок, расписаний, ошибок и истории; не имеет доступа к API-ключам Syncthing.

## 6. Тонкости интеграции с Syncthing

Syncthing предоставляет REST API, однако важны детали поведения. **Конкретные поля и способы изменения конфигурации нужно перепроверить на той версии Syncthing, которую вы зафиксируете для испытаний.**

| Потребность | Пример интерфейса Syncthing | Замечание |
|---|---|---|
| Получить конфигурацию папок | `GET /rest/config/folders` | Конфигурация ≠ текущий runtime-статус. |
| Получить конфигурацию одной папки | `GET /rest/config/folders/{id}` | ID папки локален контексту управляемого экземпляра. |
| Изменить приостановку папки | `PATCH /rest/config/folders/{id}` с полем `paused` | Менять только нужное поле; не перезаписывать целую конфигурацию без необходимости. |
| Проверить необходимость перезапуска | `GET /rest/config/restart-required` | Некоторые изменения конфигурации не применяются мгновенно. |
| Состояние папки | `GET /rest/db/status?folder=...` | Запрос может быть затратным; не опрашивать слишком часто. |
| Завершённость синхронизации | `GET /rest/db/completion?folder=...` | `100%` следует трактовать в конкретном контексте папки/узла, а не как доказательство всех прошлых доставок. |
| Соединения устройств | `GET /rest/system/connections` | Содержит информацию о соединениях, но не заменяет проверку каждой папки. |
| События | `GET /rest/events?since=...` | Возможны пропуски из-за ограниченного буфера. |

**Важно:** API `/rest/system/pause` относится к паузе устройства/устройств; для режима «по расписанию управлять определённой папкой» корректнее рассматривать конфигурацию конкретной папки. Изменение делается **на определённом экземпляре** Syncthing, а не магически сразу на всей P2P-сети.

### 6.1. Проверка результата команды

После установки `paused = true` процесс должен:

1. Сохранить намерение и назначить идентификатор операции.
2. Выполнить команду через адаптер.
3. Повторно прочитать состояние конфигурации; при необходимости проверить `restart-required`.
4. Отметить команду как **подтверждённую**, **неприменённую** или **требующую внимания**.
5. Записать время, узел, папку, правило, попытку и результат.

Получение успешного HTTP-ответа означает успешную обработку HTTP-запроса, **не обязательно завершение синхронизации или применение всех изменений**.

### 6.2. Потерянные события

`/rest/events` выдаёт события с ID и допускает `since`, но буфер событий ограничен. При разрыве связи возможно потерять часть истории. Поэтому:

- запоминать последний обработанный event ID **по каждому экземпляру**;
- при обнаружении разрыва последовательности помечать участок как неполный;
- не пытаться «догадаться» о содержимом пропущенных событий;
- после восстановления соединения сверять текущее состояние с конфигурацией и сохранять snapshot.

### 6.3. Что именно означает «последняя успешная синхронизация»

В интерфейсе лучше показывать **«последнее наблюдаемое состояние: актуально»** и время этого наблюдения. Без дополнительного протокола пробных файлов/событий нельзя достоверно утверждать, что конкретный файл доставлен в конкретную миллисекунду. Для MVP используйте аккуратные формулировки.

## 7. Правила синхронизации: рекомендуемая модель

**Минимальный тип правила:** разрешать работу папки в заданные дни недели и временные интервалы, вне окон — приостанавливать. Управление действует на **пару `(управляемый экземпляр, ID папки)`**.

Пример правила:

```json
{
  "node_id": "node-a",
  "folder_id": "project-docs",
  "timezone": "Europe/Amsterdam",
  "days_of_week": [1, 2, 3, 4, 5],
  "start_time": "01:00",
  "end_time": "06:00",
  "enabled": true
}
```

Это пример структуры данных, **не обязательно окончательный контракт API**.

### 7.1. Desired state и actual state

| Состояние | Значение |
|---|---|
| `desired_paused` | Что должно быть по активному правилу прямо сейчас. |
| `actual_paused` | Что показал Syncthing при последней проверке. |
| `last_seen_at` | Когда последний раз удалось проверить узел. |
| `last_apply_status` | `applied`, `failed`, `pending`, `unknown`. |

**Правило устойчивости:** после перезапуска backend или восстановления доступа к устройству **не воспроизводить слепо старые команды**. Сначала вычислить правильное состояние **на текущий момент**, затем привести устройство к нему.

### 7.2. Сложные случаи, которые нужно решить до реализации

- **Часовые пояса и переход на летнее время:** хранить время в UTC для истории и IANA time zone для правил; отдельно определить поведение двусмысленных/несуществующих местных часов.
- **Пересекающиеся правила:** в MVP запрещать конфликтующие активные правила для одной пары узел–папка. Не строить сложную систему приоритетов.
- **Ручное изменение настройки вне вашей панели:** на следующем опросе выявлять расхождение. В MVP выбранная политика — активное правило снова устанавливает рассчитанное значение, с записью этого факта.
- **Недоступный узел:** статус `pending/unknown`, ограниченные повторные попытки; не записывать успешное применение.
- **Повторение команды:** операцию можно безопасно повторить; повторная установка того же значения не должна создавать «ложное» изменение состояния.
- **Несколько планировщиков одновременно:** обеспечить единственного активного исполнителя (для MVP один worker-процесс; при расширении — блокировки/лидерство). Иначе возможны дубли команд.
- **Окно завершилось, но файлы не досинхронизированы:** не обещать, что все изменения успеют передаться; режим по расписанию сознательно допускает отставание.
- **Рестарт Syncthing:** проверять необходимость рестарта после изменения конфигурации и не выполнять его автоматически без специального решения.

## 8. Данные и пример схемы БД

Рекомендуется **PostgreSQL**. Для MVP достаточно SQLAlchemy и Alembic. Не нужно одновременно вводить отдельное хранилище временных рядов.

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `managed_nodes` | `id`, `display_name`, `connection_type`, `last_seen_at`, `status` | Управляемые экземпляры Syncthing. |
| `folders` | `id`, `node_id`, `syncthing_folder_id`, `label`, `observed_paused` | Папки конкретного экземпляра. Уникальная пара `(node_id, syncthing_folder_id)`. |
| `sync_rules` | `id`, `folder_id`, `timezone`, `days`, `time_from`, `time_to`, `enabled` | Правила; в MVP не больше одного активного правила на папку. |
| `command_executions` | `id`, `rule_id`, `node_id`, `desired_paused`, `attempted_at`, `verified_at`, `status`, `error_code` | Полная история применения и проверки команд. |
| `sync_events` | `id`, `node_id`, `source_event_id`, `event_type`, `occurred_at`, `received_at`, `payload_summary` | События с защитой от дублей по `(node_id, source_event_id)`. |
| `status_snapshots` | `id`, `node_id`, `folder_id`, `observed_at`, `status`, `completion`, `need_bytes`, `connected` | Периодические точки истории и источник простых графиков. |
| `app_users` | `id`, `login`, `password_hash`, `is_active` | Один или несколько администраторов. Можно оставить минимальную модель. |

**Важно:** API-ключи Syncthing и пароли **не хранить в открытом виде в БД или логах**. В демонстрационном окружении можно передавать секреты через переменные окружения или менеджер секретов; в БД — только идентификатор записи/способа доступа, если он нужен.

### Минимальная аналитика на реально доступных данных

Включить **не менее двух** собственных показателей:

1. **Доля успешных попыток применения правил** = подтверждённые команды / все завершённые попытки за период (отдельно учитывать `unknown`).
2. **Число/частота зафиксированных ошибок** по узлу и папке за сутки/неделю.
3. **Наблюдаемая доступность** = доля успешных проверок состояния среди запланированных проверок; подписать, что это показатель доступности **по наблюдениям**, а не фактический uptime без погрешности.
4. **Время до подтверждения команды** = `verified_at - attempted_at` для успешно подтверждённых применений.

Графики: лента событий и ошибок, число ошибок по дням, процент успешных применений правил, периоды отсутствия связи. **Не заявлять ML или прогнозирование как часть MVP.**

## 9. Собственный REST API и интерфейс

Это **примерные** маршруты вашего backend (не Syncthing API):

```text
GET    /api/nodes
POST   /api/nodes
GET    /api/nodes/{id}
GET    /api/nodes/{id}/folders
GET    /api/rules
POST   /api/rules
PATCH  /api/rules/{id}
DELETE /api/rules/{id}
GET    /api/events?node_id=...&from=...&to=...
GET    /api/executions?rule_id=...
GET    /api/analytics/summary?from=...&to=...
```

Рекомендуемые экраны:

1. **Обзор:** карточки управляемых экземпляров, время последнего контакта, число проблем.
2. **Папки:** текущий статус и признак приостановки; различать «неизвестно» и «исправно».
3. **Правила:** создание, изменение, включение/отключение расписаний.
4. **История:** попытки выполнения, ошибки, события и фильтры.
5. **Статистика:** 2–3 метрики и график активности.

**Рекомендация по фронтенду:** если времени мало, подойдёт простой HTML/JavaScript с шаблонами или небольшой фреймворк. Не делать сложный SPA обязательным требованием; главная ценность проекта — серверная логика, автоматизация и контроль.

## 10. Безопасность и ограничения

- **Не публиковать REST API Syncthing в открытом интернете.** Он даёт широкий контроль над конфигурацией и потенциально раскрывает чувствительные сведения.
- Backend обращается к API через **закрытую Docker-сеть, localhost или проверенный защищённый канал**. При удалённом управлении необходима отдельная схема доверия; локальный helper/agent может подключаться к серверу по исходящему HTTPS.
- Веб-панель должна требовать авторизацию; публичная регистрация не нужна.
- Использовать HTTPS для внешнего интерфейса; секреты — вне Git и логов.
- Не допускать произвольный ввод сетевого адреса для backend-прокси без проверки (риск SSRF). Управляемые адреса задаются администратором и проверяются/ограничиваются.
- Не включать опасные операции (`reset`, массовое удаление, изменения файлов/папок) в MVP.
- Для тестов использовать **только отдельные демонстрационные каталоги**, никогда реальные личные папки.
- По возможности хранить агрегированные метаданные, а не полные пути и имена пользовательских файлов.
- Предусмотреть очищение тестовой среды без затрагивания реальных файлов.

## 11. Agentic development, harness и validation

Здесь важно **не смешивать понятия**:

- **Syncthing/локальный агент:** служебная программа, взаимодействующая с API Syncthing; при наличии — часть архитектуры продукта.
- **AI coding agent:** инструмент, который помогает команде проектировать, писать и тестировать код; **не является функцией готового продукта**.
- **Development harness:** инструкции, подготовленное окружение, команды и ограничения, в которых работает coding agent.
- **Validation:** объективные проверки результата, а не оценка «агент сказал, что всё готово».

Реальный harness уже подготовлен в репозитории: машинные карточки, локальные
навыки, проверка границ и worktree, Git hooks и CI. Подробности — в
`docs/harness.md`. Примеры ниже описывают продуктовые проверки будущих этапов.

### 11.1. Минимальная структура репозитория

```text

│   ├── app/
│   │   ├── api/

│   │   ├── scheduling/

│   │   ├── analytics/

│   ├── unit/
│   ├── integration/
│   └── e2e/

│   ├── requirements.md
```

### 11.2. Что написать в `AGENTS.md`

- Сначала читать `docs/requirements.md` и соответствующие модули.
- Не переписывать архитектуру и контракты API без явной задачи.
- Не менять секреты и deployment credentials.
- При изменении бизнес-логики добавлять/обновлять тесты.
- Внешний API Syncthing использовать через адаптер; не дублировать HTTP-вызовы в нескольких модулях.
- Тесты не должны обращаться к личным папкам и «боевым» экземплярам Syncthing.
- После изменения запускать `scripts/validate.sh` и сообщать о непрошедших проверках.
- Для изменений, влияющих на конфигурацию папок, обязательно проводить ручной review.

### 11.3. Команда валидации

Например, на этапе, когда соответствующие инструменты уже настроены:

```bash
#!/usr/bin/env bash
set -euo pipefail
python -m pytest tests/unit tests/integration
python -m ruff check backend
python -m mypy backend/app
```

**Важно:** `mypy` разумно включить как обязательный gate после базовой типизации; до этого — можно запускать отдельно, чтобы не блокировать весь MVP. CI должен запускать проверки в воспроизводимом окружении. E2E с реальными контейнерами Syncthing удобнее проводить отдельным заданием CI или локально.

### 11.4. Как доказать использование агентской разработки в отчёте

Для 2–3 реальных задач сохранить короткий журнал:

| Поле | Пример |
|---|---|
| Задача | «Реализовать сверку desired/actual paused» |
| Требования | F-05, F-06 |
| Работа coding agent | Какие файлы он анализировал и изменил |
| Валидация | Какие команды/тесты запускались |
| Ошибки и исправления | Что было найдено автоматическими проверками |
| Контроль человека | Какие изменения приняли или исправили вручную |
| Ссылка | Commit/PR в репозитории |

Это демонстрирует **управляемую агентскую разработку**, а не просто факт использования чат-бота.

## 12. Тестовое окружение и план проверок

**Минимальный тестовый стенд:** два изолированных Syncthing в Docker, две тестовые директории, backend и PostgreSQL. Файлы сгенерированы для эксперимента; доступ к реальным файлам пользователя отсутствует.

| ID | Проверка | Критерий успешности |
|---|---|---|
| T-01 | Подключение к двум узлам | Оба узла отображаются и имеют корректные локальные папки. |
| T-02 | Обычная синхронизация | Созданный в тестовой папке файл появляется на другом узле и совпадает по контрольной сумме. |
| T-03 | Пауза папки | При активной паузе конкретной папки новая тестовая правка не синхронизируется в пределах контрольного интервала. |
| T-04 | Возобновление | После снятия паузы ожидаемый файл появляется и совпадает по хешу. |
| T-05 | Недоступность | При отключении API узла панель показывает недоступность, не подменяя её успешным состоянием. |
| T-06 | Возврат узла | После подключения вычисляется актуальное правило и подтверждается применение нужного состояния. |
| T-07 | Дубли события | Повторно полученный `source_event_id` не создаёт второй логический event. |
| T-08 | Пропуск события | Разрыв последовательности фиксируется, запускается сверка состояния. |
| T-09 | Некорректные правила | Невалидные интервалы и конфликтующие активные правила отвергаются. |
| T-10 | Неверный API-ключ | Операция завершается безопасной ошибкой; секрет не попадает в журнал. |
| T-11 | Перезапуск backend | Правила сохраняются, scheduler после старта вычисляет текущее состояние. |
| T-12 | Авторизация | Неавторизованный клиент не может изменять конфигурацию. |
| T-13 | Аналитика | Агрегации соответствуют заранее подготовленному небольшому набору событий. |

Для реального E2E нужны **таймауты ожидания и повторные проверки**, а не фиксированное `sleep(1)` с предположением, что файловая синхронизация всегда мгновенная. Измерения времени и задержек в тестах — фактические, не гарантируемые.

### Уровни тестирования

- **Unit:** правила времени, конфликтность, расчёт desired state, аналитика.
- **Contract:** адаптер правильно обрабатывает ответы REST API и ошибки (моки/фикстуры).
- **Integration:** приложение + PostgreSQL + реальные Syncthing-контейнеры.
- **End-to-end:** пользователь создаёт правило в UI, оно применяется, изменения отражаются в истории.
- **Security smoke:** защита API, отсутствие секретов в логах, невозможность несанкционированной команды.

## 13. Этапы реализации и условия готовности

| Этап | Что сделать | Демонстрируемый результат |
|---|---|---|
| 1. Исследование и прототип | Запустить два Syncthing, вручную проверить API и смену `paused` | Управление тестовой папкой через API подтверждено. |
| 2. Каркас | FastAPI, PostgreSQL, модели, миграции, Docker | Сервер и БД запускаются одной командой. |
| 3. Подключение и сбор | Адаптер, реестр узлов/папок, события, snapshots | Данные двух узлов отображаются через API. |
| 4. Правила | Сохранение расписания, вычисление желаемого состояния, reconciliation | Пауза/возобновление реально срабатывает. |
| 5. Интерфейс и аналитика | Экран узлов, правила, история, 2–3 метрики | Полный пользовательский сценарий без ручных вызовов API. |
| 6. Проверка и защита | Unit/интеграционные/E2E тесты, CI, VPS, отчёт | Проект воспроизводим, тесты зелёные, защита демонстрируема. |

### Definition of Done для курсовой

Работу можно считать готовой, если:

- два тестовых узла действительно синхронизируют файлы;
- собственный backend получает их состояние и хранит историю в БД;
- из UI можно создать и отключить правило;
- правило изменяет поведение **реального** Syncthing, а система подтверждает или корректно фиксирует ошибку;
- обрыв связи и последующее восстановление обработаны без «ложного успеха»;
- есть минимум два собственных аналитических показателя;
- есть unit- и интеграционные тесты, зафиксирован agentic development workflow;
- проект развёрнут на VPS, исходники доступны в репозитории, отчёт содержит схемы, тест-кейсы и скриншоты.

## 14. Распределение на двух участников

| A / playerboom (друг): интеграция и данные | B / danilsdk (ты): автоматизация и интерфейс |
|---|---|
| Syncthing Adapter | Rule Engine / Scheduler |
| Реестр узлов и папок | Reconciliation и история выполнения команд |
| FastAPI и модели PostgreSQL | Интерфейс обзора и настройки правил |
| Сбор событий и snapshots | Минимальная аналитика и визуализация |
| Контрактные и API-тесты | Unit-тесты правил и UI-тесты |

**Совместно:** архитектурные решения, Docker Compose, E2E стенд, CI, интеграция, развёртывание и отчёт. Важно не отдавать одному участнику только «рисование интерфейса»: логика правил и проверка их исполнения — отдельная существенная часть работы.

Распределение участников уточнено: владелец текущего проекта danilsdk выполняет
роль B, напарник playerboom — A. Точный процесс и исключения из владения —
в `docs/teamwork.md`, исполняемые инструкции — в `docs/harness.md`. Harness
поддерживает B; продуктовый стенд и общую схему данных поддерживает A.

### Как делить работу по Git

- Согласовать схемы DTO и контракты API до параллельной разработки.
- Разделить директории/пакеты по зонам ответственности.
- Работать через ветки и pull request / merge request, использовать review друг друга.
- В CI запускать общую validation-команду на каждое изменение.
- Не хранить `.env` с реальными ключами; публиковать только `.env.example`.

## 15. Что может сорвать сроки и как этого избежать

| Риск | Как снизить |
|---|---|
| Трудно безопасно обращаться к удалённым домашним компьютерам | Сначала изолированный тестовый стенд; агент удалённого доступа — расширение. |
| Неожиданные различия между версиями Syncthing | Зафиксировать версию/тег контейнеров, сохранить реальные примеры JSON-ответов. |
| Изменили конфигурацию, но она не применилась | Проверять состояние после операции и `restart-required`. |
| Неоднозначные события и пропуски | Периодические snapshots, хранение `source_event_id`, маркировка неполной истории. |
| Параллельные/конфликтующие расписания | Для MVP одно активное правило на пару узел–папка. |
| Переоценили точность статистики | Чёткие определения метрик; отсутствие наблюдений не равно доступности. |
| Слишком много UI | Сначала простой интерфейс; приоритет ядра автоматизации. |
| Лишние небезопасные операции | Не поддерживать массовое удаление/сброс, тестировать только на демонстрационных данных. |
| Два участника мешают друг другу | Согласованные API-контракты, независимые модули, единый CI. |

## 16. Как оформить курсовую по имеющейся методичке

В предоставленных методических указаниях для командного практико-ориентированного проекта обозначены серверная и клиентская части, БД/CRUD, тестовое окружение, VPS и публикация репозитория. Команда — 2–3 студента, каждый делает минимум один модуль. Для командной работы указан отчёт порядка **20–25 страниц**.

Рекомендуемая структура отчёта:

1. Титульный лист и аннотация с вкладом каждого студента.
2. Цель, задачи, предметная область, анализ Syncthing и близких решений.
3. Обоснование технологий.
4. Архитектура, диаграмма модулей и схема БД.
5. Реализация: интеграция, правила, модель состояний, события, аналитика.
6. Agentic development и устройство harness — что делал AI-агент, как проверялся код, как участвовал человек.
7. Тестовое окружение, тест-кейсы и **реальные** результаты.
8. Демонстрация UI, развёртывание, скриншоты и описание сценариев.
9. Выводы, ограничения и ссылка на репозиторий.

**На согласовании стоит уточнить:** достаточно ли веб-панели в роли клиентской части или отдельно нужен Telegram-бот. В методичке присутствует неоднозначная формулировка по индивидуальной и командной работе; не стоит обещать дополнительный интерфейс без подтверждения.

## 17. Решения, которые можно менять в процессе

**Зафиксировать с самого начала:** предметная задача, использование Syncthing как механизма передачи, собственный сервер и БД, правила автоматизации, история выполнения, проверки и безопасность.

**Оставить гибкими:** Vue/React/серверные шаблоны, APScheduler или отдельный worker, точные названия таблиц и API-маршрутов, вид графиков, способ размещения тестовых узлов, наличие удалённого helper/agent, Telegram и экспорт отчётов.

Таким образом, проект остаётся содержательным даже при упрощении отдельных функций.
