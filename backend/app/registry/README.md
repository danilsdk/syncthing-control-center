## Девять операций существующего OpenAPI

| Метод | Маршрут | operationId | Успешный ответ |
|---|---|---|---|
| POST | /api/auth/login | login | 200 Session + cookie |
| GET | /api/auth/me | current_session | 200 Session |
| POST | /api/auth/logout | logout | 204, удаление cookie |
| GET | /api/connections | list_connections | 200 ConnectionPage |
| GET | /api/nodes | list_nodes | 200 NodePage |
| POST | /api/nodes | register_node | 201 Node |
| GET | /api/nodes/{node_id} | get_node | 200 Node |
| PATCH | /api/nodes/{node_id} | update_node | 200 Node |
| GET | /api/nodes/{node_id}/folders | list_folders | 200 FolderPage |

Login публичный, остальные восемь операций требуют активного администратора.
Все изменения, включая login, проверяют Origin; после входа — ещё CSRF.
Страницы используют limit=50 (1–100), offset>=0 и total после фильтров.
Connections/узлы сортируются по display_name и стабильному второму ключу
(connection_ref для connections, id для nodes); папки — created_at,id DESC.
Все времена публичного API — UTC Z, поля и правила PATCH берутся из готовых DTO.

### A2.2: выбранный минимальный вариант auth

1. Один администратор создаётся явной локальной командой модуля
   `python -m app.registry admin-create`. Пароль вводится через getpass, не через
   аргумент командной строки. Никакого автоматического создания/миграции при
   старте API. Операция под транзакционной блокировкой app_users не создаёт
   второго пользователя; существующие записи не перезаписываются молча.
2. AppUser.password_hash хранит версионированный профиль scrypt из hashlib:
   N=2**17, r=8, p=1, salt=16 случайных байт, dklen=32, maxmem=256 MiB.
   Соль/хеш кодируются в строке с фиксированным профилем. Произвольные параметры
   из повреждённой строки не исполняются. Пароли не обрезаются/не нормализуются;
   при создании — минимум 15 символов, максимум соответствует Login (1024).
   Логин администратора — нормализованный ASCII по существующему DB CHECK.
3. Подписанная cookie scc_session: фиксированный HMAC-SHA256 из stdlib, отдельный
   домен подписи `scc:admin-session:v1`, строгий base64url и ограниченный размер
   (не более 2048 байт). Полезная нагрузка содержит только UUID пользователя,
   абсолютный expires_at и случайный CSRF-токен. Алгоритм не берётся из cookie.
   Подпись проверяется до доверия payload, сравнения — hmac.compare_digest.
   Это подпись, не шифрование: секреты в cookie не помещаются.
4. Срок — 8 часов без продления от чтений; expires_at <= now означает отказ.
   Clock внедряется для проверок. На каждом защищённом запросе читается AppUser:
   удалённый/неактивный пользователь не получает доступ. Cookie: HttpOnly,
   SameSite=Lax, Path=/, без Domain, Secure в production/HTTPS-настройке.
   Секрет подписи задаётся сгенерированным серверным значением вне Git.
5. Origin сравнивается с Settings.allowed_origins. Его отсутствие/чужое значение
   дают 403 origin_forbidden, не случайный 422 от обязательного Header.
   У авторизованных POST/PATCH/PUT/DELETE отсутствие/несовпадение X-CSRF-Token
   даёт 403 csrf_invalid. Приоритет: для защищённого запроса сначала сессия,
   затем Origin/CSRF, затем предметные зависимости и работа с источником.
6. Неверный логин, пароль или inactive при входе дают одинаковый 401 invalid_credentials;
   неизвестный логин проходит dummy-проверку того же KDF-профиля. Недостающие
   настройки/администратор дают закрытый 503 auth_not_configured. Нет подходящей
   сессии у защищённого маршрута — 401 authentication_required. Ошибка БД —
   безопасный 503 service_unavailable. Пароль/cookie/CSRF не попадают в журнал.
7. Для одного API-процесса — 5 попыток за 60 секунд на peer IP и 30 за 60 секунд
   суммарно; один KDF одновременно, превышение/занятость — 429 login_rate_limited.
   Ограничитель использует монотонное время, lock, TTL и не более 1024 IP-записей;
   при переполнении отказывает, а не создаёт неограниченную память. Перед KDF
   резервируется попытка; чужим X-Forwarded-For не доверяем. Несколько API workers
   потребуют общего ограничителя: это отдельное расширение, не заявленная защита MVP.
8. Login/me возвращают готовый Session DTO; auth-ответы не кешируются.
   Logout проверяет доступ/Origin/CSRF и удаляет cookie с теми же Path/Domain.
   Серверного списка сессий в MVP нет: logout удаляет браузерную cookie, скопированный
   токен действует до срока, деактивации пользователя или смены секрета подписи.
   После смены пароля оператор также меняет секрет для отзыва прежних сессий.

Выбор scrypt использует доступный OpenSSL Python 3.12 без новой зависимости.
[Профиль OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt)
применён как инженерное решение MVP; Argon2id остаётся вариантом при расширении зависимостей.
[Python hashlib](https://docs.python.org/3.12/library/hashlib.html#hashlib.scrypt)
определяет scrypt/maxmem;
[Python hmac](https://docs.python.org/3.12/library/hmac.html#hmac.compare_digest)
— сравнение подписей. Возможность выбранного scrypt проверена на текущем Python
3.12.14/OpenSSL 3.5.8: около 2 секунд на публичной пробе. Это не SLA и не
измерение VPS; память/задержку повторно оценивают в A4.

### A2.3: регистрация, чтения и наблюдения

**Регистрация.** API принимает только NodeCreate: connection_ref/display_name.
URL и ключ берутся из Settings.connections. Сначала проверяется псевдоним и
существующая регистрация; неизвестный alias — 422 connection_not_allowed, дубликат —
409 connection_already_registered. Названия не превращаются в URL. Для нового UUID
создаётся временный клиент A1: обнаруживается Device ID, затем обязательные
чтения выполняются с закреплённой identity. Успешные system/config наблюдения
проверяются на одну эпоху до/после чтений. Сетевой I/O не удерживает транзакцию.

Только после успешных обязательных чтений одна DB-транзакция сохраняет узел,
папки и исходный checkpoint с last_event_id=0. Ошибка обязательного источника
не оставляет частично зарегистрированных строк. Гонка двух POST разрешается
уникальностью connection_ref и rollback с 409. Пустой корректный список папок
допустим. Runtime — отдельное best-effort наблюдение, не условие регистрации.
Адаптер уже проверяет DisplayName для папок; сырые непригодные labels не чинятся
молчаливым обрезанием в сервисе.

**Чтения.** GET списка узлов и connections читают серверную конфигурацию/БД,
без сетевого обхода всех узлов. GET конкретного узла/его папок может обновить
наблюдения только этого enabled-узла, если после last_checked_at прошло
observation_interval_seconds (30 секунд по умолчанию). До истечения интервала
возвращается кеш. Для disabled нет сетевого запроса; данные сохраняются как stale.
Это обновление кеша наблюдений, не изменение конфигурации Syncthing.

Проверка одного узла вынесена в RegistryService.refresh_node. Сеть выполняется
через A1 вне DB-транзакции и event loop; запись короткой транзакцией под
блокировкой строки узла повторно проверяет enabled/identity/конфигурацию и
порядок last_checked_at, чтобы запоздавшее наблюдение не затёрло более новое.
Разрешённые подключения в MVP используют адреса частного стенда; отдельная
отмена системного DNS и общий SLA метода адаптером не обещаются.

На успешной проверке обновляются last_checked_at/last_seen_at. На ошибке —
last_checked_at/api_status, прежние значения и времена папок сохраняются.
Для уже зарегистрированного узла отказ источника возвращает доступный Node/Folder
со stale-признаками, а не стирает строку. Ошибка БД остаётся HTTP 503.
Timeout/unreachable отображаются в существующий api_status=unreachable;
auth_error/identity_mismatch/invalid_response сохраняют соответствующие значения,
неустановленная непрерывность session_changed — unknown. Новые enum не вводятся.

Папки сопоставляются по (node_id, syncthing_folder_id), UUID не пересоздаются.
present=false выставляется только после полного успешного чтения списка с
правильной identity; история/правила не удаляются. Возвращённая папка использует
прежний UUID. is_stale для конфигурации учитывает отсутствие данных, порог
stale_after_seconds, последнюю ошибку узла, disabled и present=false.
Runtime имеет отдельные значения/время: ошибка не обновляет время старого runtime;
если успешного runtime ещё не было, остаётся null. Пустой state paused-папки
Syncthing 2.1.7 не превращается в idle; успешный paused config остаётся читаемым.
Состояние API узла определяется обязательными system/config чтениями; ошибка
отдельного runtime не объявляется свежим успешным runtime-наблюдением.

PATCH меняет только display_name/enabled, не connection_ref/Device ID и не paused.
Изменение enabled влияет на последующие циклы исполнителя; уже отправленная
команда не отменяется магически. B2 обязан перечитывать ограничения перед записью.

**Граница D-01.** Resolver заново читает managed_nodes и доверенную connection_ref,
строит NodeConnection по внутреннему UUID, закрепляет сохранённый Device ID и
восстанавливает SourceCheckpoint из raw start time / session / anchor.
Anchor=null остаётся недоказанным legacy-состоянием. Удалённый alias или неверная
identity запрещают использование старого кешированного клиента.
После первоначальной регистрации A2 не меняет last_event_id, source_session_id,
source_start_time_raw или source_stream_anchor при чтении статуса. Их атомарная
запись с событиями/границами принадлежит A3; runtime/checkpoint — разные данные.

**Граница B1.** Folder DTO требует пару desired_paused/active_rule_id одновременно
null или одновременно заполненную. A2 не вычисляет расписание самостоятельно.
Без активного правила оба null. При наличии активного правила проекция требует
подключённого вычислителя B1 (в тестах — внедрённого fake); без него — безопасный
503 service_unavailable, а не ложное отсутствие правила или desired=actual.
Подключение принятого B1 выполняется при интеграции, код B здесь не изменяется.

**Ошибки регистрации.** Timeout — 504 upstream_timeout; недоступность —
502 upstream_unreachable, неверный ключ — 502 upstream_auth_error,
плохой ответ или identity — 502 upstream_invalid_response;
потеря непрерывности до согласованного чтения — безопасный 503 service_unavailable.
HTTP-коды/имена сверяются с разделом 9 контракта при реализации. Тексты источника,
адреса, ключи и пути в Error/request_id не включаются.
Отсутствующий узел приложения — 404 node_not_found. Общий resolver-helper A0/A6
не заменяет проверку существования записи и предметный код ошибки маршрута.

## Запуск реализованной авторизации A2.2

Используется Python 3.12 с установленным backend. Сначала настройте собственную
SCC_DATABASE_URL и примените миграции по
[инструкции A0.3](../../../docs/design/a/a03-runbook.md).
CLI проверяет готовность схемы и не создаёт её автоматически.
Из корня выбранного checkout (локальный пример PowerShell):

```powershell
$env:PYTHONPATH = (Resolve-Path backend).Path
# Сгенерировать один раз; сохранить вне Git и повторно использовать при запуске API.
$env:SCC_SESSION_SECRET = python -c "import secrets; print(secrets.token_urlsafe(32))"
python -m app.registry admin-create --login admin
python -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000 --workers 1 --no-access-log --no-proxy-headers
```

Пароль и подтверждение CLI запрашивает через getpass. Повторный bootstrap
не меняет существующий пароль и не добавляет второго администратора.
Пароль в аргументах не поддерживается; ошибка разбора аргументов не повторяет
полученные значения. Неполадки БД/закрытия ресурсов выводятся фиксированным текстом.
В разработке настоящий администратор пользователя не создавался: проверки
использовали только собственную временную БД с тестовыми данными.

POST /api/auth/login получает Login JSON и разрешённый Origin, устанавливает
HttpOnly cookie, возвращает Session с CSRF. GET /api/auth/me возвращает тот же
срок и CSRF без продления. POST /api/auth/logout требует Origin/CSRF и удаляет
cookie. Login проверяет Origin до JSON; ошибки используют общий Error
и X-Request-ID. Ответы /api/* получают Cache-Control: no-store.

По умолчанию допустим Origin http://localhost:8000. Для HTTPS выставляют
production и явный SCC_ALLOWED_ORIGINS; Secure включается для production,
HTTPS-запроса или конфигурации только с HTTPS origins. Настройка reverse proxy,
доверенных forwarded IP и общего лимитера при нескольких процессах относится
к расширению стенда. Этот пример запускает один API-процесс напрямую.

create_app принимает необязательный auth=AdministratorAuth для явного тестового
внедрения. По умолчанию используются AdminStore/Database и общий Clock; создание
приложения не читает БД, не запускает KDF и не создаёт пользователя. Роутеры B
по-прежнему подключаются через routers под общей require_admin. Подпись cookie,
пароли и limiter — registry/security.py, SQL — registry/admin.py,
сервис — registry/authentication.py, HTTP/заголовки — api/auth.py.

## Использование реестра A2.3

До запуска API задайте SCC_CONNECTIONS серверным JSON-словарём. Ключ каждой
записи — connection_ref; значение содержит display_name, base_url и api_key.
Секреты берутся из защищённой конфигурации стенда вне Git. GET /api/connections
показывает только connection_ref/display_name. Браузер не передаёт URL или API-ключ.

После login сохраните cookie и CSRF из Session. Зарегистрируйте каждый выбранный
alias через POST /api/nodes с NodeCreate, разрешённым Origin и X-CSRF-Token:

```json
{"connection_ref":"demo-a","display_name":"Демонстрационный узел A"}
```

Успех — 201 Node с внутренним UUID. Сначала выполняются обязательные чтения
источника; затем узел и полный список папок записываются атомарно. Дубликат alias
даёт 409; ошибка проверки не оставляет частичной регистрации.

GET /api/nodes возвращает кеш БД. GET /api/nodes/{node_id} и
GET /api/nodes/{node_id}/folders обновляют выбранный enabled-узел при истечении
интервала (по умолчанию 30 секунд). При ошибке связи старые значения сохраняются
со stale-признаком. Возраст свыше 60 секунд по умолчанию также означает stale;
ровно 60 секунд ещё не превышает порог. Неизвестный runtime остаётся null.
PATCH /api/nodes/{node_id} принимает только display_name/enabled; конфигурацию
Syncthing, включая paused, эти маршруты не меняют.

Внутренний NodeResolver перечитывает сохранённые identity/checkpoint перед
выдачей адаптера. Device ID закреплён регистрацией. Последующие чтения и PATCH
не меняют канонические epoch/anchor/cursor A3. Для desired-state активного правила
нужно внедрить RegistryService(desired_state=...) с вычислителем B1; до интеграции
активное правило без вычислителя даёт безопасный 503.

create_app по умолчанию собирает HttpAdapterFactory/NodeResolver при непустом
SCC_CONNECTIONS и закрывает фабрику вместе с БД. Для проверок допускается явное
внедрение registry=RegistryService. Старт приложения не читает источники и не
запускает исполнитель.

## Повтор проверок

```powershell
python -m pytest -c backend/pyproject.toml tests/unit tests/contract tests/integration/auth tests/integration/registry -m "not postgres" -q -W error
python tests/integration/auth/check_postgres.py --bin-dir "C:\Program Files\PostgreSQL\18\bin" --suite all
```

Первая команда включает прежние unit/contract и новые auth/registry-компоненты.
Вторая создаёт отдельный кластер, мигрирует, проверяет настоящие SQL/CLI/KDF,
реестр с подставными Syncthing и останавливает/удаляет только собственный кластер.
Для отдельного запуска доступны --suite auth и --suite registry; по умолчанию auth.
Адрес рабочей БД не принимается. Тесты с подставными источниками и реальный стенд
имеют отдельные отчёты.
Повтор A2 проверяет auth/registry на принятой схеме. Отдельные проверки схемы
A0/D01 имеют собственные доказательства; их повтор не подменяется этим запуском.

## Реальная проверка A2.4 и передача

Из корня checkout с установленным backend и подготовленным приватным стендом A1:

```powershell
$env:PYTHONPATH = (Resolve-Path backend).Path
python tests/integration/auth/check_postgres.py --bin-dir "C:\Program Files\PostgreSQL\18\bin" --suite registry-live --live-report "$env:TEMP\scc-a24-report.json"
```

Проверка откажется запускаться, если стенд уже работает. Она создаёт собственную
пустую БД, мигрирует её, создаёт временного администратора с настоящим scrypt и
запускает один процесс Uvicorn на случайном loopback-порту. Подмен auth/registry/
Clock/адаптера нет. Интервал наблюдения в этой проверке — 1 секунда вместо
обычных 30, порог stale остаётся 60 секунд. Ожидания ограничены сроком и повторными
наблюдениями. При старте стенд A1 восстанавливает свою демонстрационную конфигурацию.

Проверены все девять операций A2: вход/me/выход, защита read/write, Origin/CSRF,
отклонение лишних полей, два узла с четырьмя разными внутренними UUID папок,
отказ регистрации с неверным ключом без частичных строк, дубликат 409, пагинация
и PATCH. Тест временно меняет paused одной demo-папки через адаптер и наблюдает
null runtime у paused-источника; затем снимает паузу и наблюдает runtime.
Так проверяется различие неизвестного состояния и недоступности узла.

После остановки только узла A его последние значения/времена сохраняются со stale,
узел B остаётся доступен. Перезапуски API с подменённым серверным подключением
и неверным ключом дают identity_mismatch/auth_error без замены закреплённого ID.
После настоящего перезапуска источников и API прежние UUID/имя/PATCH сохранены,
дублей нет. Эпоха источника действительно изменилась, канонический checkpoint A3
остался прежним. Выход удаляет браузерную сессию, новый вход успешен.

В конце сравнивается полная конфигурация demo-папок с исходной, останавливаются
только принадлежащие проверке процессы и удаляется частный PostgreSQL. Пароль,
хеш, секрет подписи, API-ключи, целевые URL/закрытые home-пути проверяются на отсутствие
в телах ответов и журнале API; cookie/CSRF — на отсутствие в журнале и отчёте.
Санитизированный [отчёт реального стенда](../../../tests/integration/registry/evidence-live-v2.1.7.json)
содержит результат, время и хеши проверенных исходников. Локальные XML и расширенная
сверка остаются вне Git, пути указаны в журнале A2.

| Потребитель | Что использовать и учитывать |
|---|---|
| A3 | NodeResolver(settings, database), поля checkpoint managed_nodes; A2 после регистрации не продвигает курсор. Сохранять эпоху/anchor/cursor атомарно с событиями и границами |
| B1 | Внедрить чистый вычислитель desired_state(rule, now) -> bool в RegistryService; активное правило без него даёт 503. A2 не вычисляет расписания |
| B2 | Получать адаптер по внутреннему UUID, перечитывать enabled/актуальное правило перед записью. PATCH enabled не отменяет уже отправленную команду |
| B3 | Login с Origin; cookie автоматически, CSRF из Session для изменений. Списки имеют limit/offset/total, ошибки — Error + request_id. Показывать null/runtime timestamp и stale раздельно |
