# Syncthing Control Center: инструкции для агентов проекта

## Участники проекта и состояние

- **B / danilsdk — участник проекта, ответственный за автоматизацию и интерфейс.**
- **A / playerboom — участник проекта, ответственный за интеграцию и данные.**
- В проекте настроен development harness. Функциональность приложения ещё не
  реализована.
- Прямое поручение участника проекта, данное для текущей задачи, имеет приоритет
  над настоящими инструкциями. Такое поручение может разрешать изменение общей
  зоны; повторно запрашивать это разрешение не требуется.

## Вход в задачу

1. Прочитай `README.md`, `docs/requirements.md`, `docs/architecture.md`.
2. Для исполнения карточки используй repo skill `$scc-task`; для отдельного
   review — `$scc-review`. Если навык ещё не обнаружен текущей сессией, прочитай
   соответствующий `.agents/skills/*/SKILL.md` напрямую.
3. Получи ID задачи и прочитай `.harness/tasks/<ID>.json` вместе с её текстовым
   описанием. Машинная карточка задаёт точные разрешённые пути; сведения о
   владении — в `.harness/project.json`, общий процесс — в `docs/harness.md`.
4. Прочитай вложенные `AGENTS.md` относящихся к задаче каталогов: Codex, запущенный
   из корня, может не загрузить инструкции всех дочерних модулей автоматически.
5. Проверь ветку и состояние рабочей папки. Одна задача — одна ветка и один
   worktree. Подготовка: `python3 scripts/harness.py start <ID>` после публикации
   harness в исходной ветке. Не переключай папку другого агента.

Если участник проекта поручает настройку или новую работу вне существующих
карточек, такое поручение является основанием для создания отдельной карточки с
точными границами. Не отказывайся от разрешённой работы из-за отсутствия старой
карточки.

## Совместная работа

- Работа выполняется совместно несколькими участниками проекта. Сохраняй
  изменения других участников и учитывай их при реализации.
- Меняй только необходимые файлы задачи. Чужие файлы можно читать; предложения
  изменений передавай отдельным описанием. Продолжай независимую часть работы.
- Не расширяй `allow` в карточке для маскировки выхода за границы. Изменение
  границ оформляется отдельной явно порученной задачей и проходит review.
- Общая БД, миграции и сборка приложения принадлежат A. Расписания, исполнитель,
  аналитика и frontend — B. Harness поддерживает B. Все исключения указаны в карте.
- Не форматируй весь репозиторий с записью. Общие `__init__.py`, fixtures и
  lock-файлы изменяет их владелец; локальные фикстуры держи в зоне задачи.
- Не держи общий изменяемый список прогресса: журнал каждой задачи — отдельный
  `docs/agent-log/a/<ID>.md` или `docs/agent-log/b/<ID>.md`.
- Несколько исполняющих агентов допускаются только по прямому поручению участника
  проекта, в разных worktree и с непересекающимися областями записи. Review по
  умолчанию выполняется в режиме чтения кода.

## Инварианты продукта

- Syncthing вызывается только через `syncthing_adapter`.
- Объект управления — папка конкретного экземпляра; не путай внутренние ID
  приложения с Syncthing Device ID и Folder ID.
- Успех HTTP не подтверждает применение команды. Требуются наблюдение результата
  и отдельная запись попытки. Неизвестное/устаревшее состояние не считается успехом.
- После сбоя, перед повтором и после изменения правила пересчитывай состояние
  на текущее время. В MVP действует один исполнитель.
- История хранит UTC, расписание — IANA timezone. Семантика окон определяется
  контрактом, а не случайными допущениями в одном модуле.
- API-ключи Syncthing остаются на сервере, вне Git, браузера и журналов.
- Реальные проверки проходят только на демонстрационных папках и закрытом стенде.
  Изменение конфигурации Syncthing проверяет ответственный участник проекта до
  слияния PR.

## Проверка, commit и передача

- Выполняй `python3 scripts/harness.py validate --task <ID>` и проверки карточки.
  Для начальной настройки окружения есть `python3 scripts/harness.py setup`.
- Проверка harness не доказывает готовность приложения; fixtures не заменяют
  реальную интеграцию. Отмечай неприменимые, неуспешные и незапущенные проверки.
- До commit проверь конкретные файлы; не добавляй чужую работу через `git add .`.
  Внутри порученной задачи локальный commit после проверки допустим.
- Push/PR выполняй по прямому поручению участника проекта. Существующее разрешение
  сохраняется. Не делай force push, сброс/очистку чужой работы и прямой commit в main.
- После PR сообщи ссылку и реальные результаты. Агент автора не объединяет PR
  своей задачи. Для PR второго участника проекта действует постоянный порядок,
  описанный ниже.
- Используй `docs/templates/agent-result.md` для журнала и передачи результата.
  Сохраняй ход решений и ограничения, достаточные для продолжения после смены сессии.

## Постоянный порядок: review и merge PR вторым участником проекта

В проекте действует этот порядок, утверждённый 2026-10-15. При выполнении задачи
агент проверяет готовые PR второго участника проекта перед началом работы и перед
передачей результата. Проверка выполняется в активной сессии агента; закрытая или
ожидающая ввода сессия Codex автоматически не запускается. Авторизацию GitHub
проверяй по API текущего пользователя, а не по git user.name.

- Для задач danilsdk проверяй PR playerboom, для задач playerboom — PR danilsdk.
  Агент-рецензент вправе опубликовать содержательный review, поставить approval и
  выполнить squash merge подходящего PR без дополнительного согласования.
  Исполняющий агент не принимает собственный PR.
- Прочитай `$scc-review`, следуй порядку из `docs/harness.md#peer-agent-review`.
  `review-plan` проверяет роли, принятые границы и свежесть base; он не заменяет review.
- Слияние разрешено только для открытого ready PR в main этого репозитория,
  после полного review, применимых проверок, успешного CI и устранения замечаний.
  Сверяй точные head/base; новые изменения требуют повторной проверки.
- Не обходи защиту main, не ставь approval без проверки, не меняй код автора
  в review и не принимай отсутствие обязательных реальных проверок за успех.
- При дефектах опубликуй конкретные замечания и продолжай свою независимую работу.
  Настоящий порядок не предоставляет разрешения на отправку сообщений в другие
  сессии.
- Начальный PR H0 также может проверить и объединить агент playerboom. Пока
  harness отсутствует в main, его правила читаются из H0 и проверяются целиком.

## Code Review Rules

- Отмечай ложное подтверждение команды, потерю неизвестных состояний,
  неправильную адресацию папки и выполнение устаревшего правила после сбоя.
- Проверяй отсутствие обхода адаптера, утечки ключей и дублирующего worker.
- Проверяй согласованность DTO, схемы БД и интерфейсов потребителей.
- При review harness проверяй обход ограничений путей, работу с rename,
  использование политики базовой ветки в CI и сохранность чужих файлов.
- Выводы подтверждай файлом, строкой и воспроизводимым сценарием. Не исправляй
  код в рамках read-only review, если исправление не поручено отдельно.
