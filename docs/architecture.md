Документ описывает компоненты системы на основе [рабочего плана проекта](../syncthing_coursework_mvp_plan.md).
Целевой состав MVP и готовность отдельных модулей различаются. Состав конкретного
checkout зависит от его ветки; актуальные команды и ограничения указаны в
[README](../README.md) и журналах соответствующих этапов.

На 2026-10-27 опубликованы реализации A0–A3: каркас и БД, адаптер Syncthing,
авторизация и реестр, сбор событий и API истории. В [черновике A4 #7](https://github.com/danilsdk/syncthing-control-center/pull/7)
собраны Docker-стенд ядра и GitHub CI с настоящими PG/API/двумя Syncthing.
Эти PR ещё ожидают независимой приёмки; main не представляет готовый MVP.
Расписания B1, исполнитель B2, интерфейс B3 и аналитика B4 остаются следующими
модулями. Сбор A3 пока запускается явным проходом; общий постоянный цикл входит в A4.3.

## Компоненты

| Каталог | Назначение |
|---|---|
| `backend/app/api/` | Собственный REST API для веб-интерфейса и авторизованного управления. |
| `backend/app/registry/` | Регистрация экземпляров Syncthing и сопоставление их папок. |
| `backend/app/syncthing_adapter/` | Единственная точка обращения к API Syncthing; чтение состояния, изменение паузы, получение событий. |
| `backend/app/scheduling/` | Хранение и проверка расписаний, расчёт желаемого состояния папки на текущий момент. |
| `backend/app/reconciliation/` | Сравнение желаемого и наблюдаемого состояния, отправка команды, подтверждение результата. |
| `backend/app/collection/` | Сбор событий и периодических снимков, обработка дублей и неполной истории. |
| `backend/app/analytics/` | Расчёт показателей по событиям, наблюдениям и результатам команд. |
| `backend/app/models/` | Модели PostgreSQL для узлов, папок, правил, событий, команд и пользователей. |
| `backend/migrations/` | Версионирование схемы БД. |
| `frontend/src/` | Обзор, папки, расписания, история и статистика. |
| `deploy/` | Изолированные стенды A1/A4, конфигурация Docker Compose и будущая конфигурация VPS. |
| `scripts/` | Команды разработки и проверок; приложение и harness проверяются отдельно. |

## Целевой поток полного MVP

1. Администратор работает с веб-интерфейсом через HTTPS и авторизацию.
2. Веб-интерфейс получает служебные данные и изменяет правила через собственный REST API.
3. Планировщик рассчитывает желаемое состояние для конкретной пары «экземпляр — папка».
4. Исполнитель сверяет его с наблюдаемым состоянием, при необходимости обращается к адаптеру и проверяет результат.
5. Коллектор сохраняет события и снимки, аналитика использует историю из PostgreSQL.
6. Файлы синхронизируются средствами Syncthing между узлами независимо от веб-панели.

## Проектные решения

- Первый стенд включает backend, PostgreSQL и два экземпляра Syncthing в закрытой Docker-сети.
- API-ключи Syncthing доступны серверным компонентам и не попадают в браузер, Git или журналы.
- Внутренний ID управляемого экземпляра отличается от Syncthing Device ID; папка адресуется в контексте конкретного экземпляра.
- В MVP допускается один активный исполнитель правил и одно активное правило для пары «экземпляр — папка».
- После сбоя вычисляется актуальное желаемое состояние; старые команды не воспроизводятся без пересчёта.
- Конфигурация, наблюдаемое состояние и подтверждение команды учитываются раздельно.
- Отсутствие данных означает неизвестное состояние; пропуски событий отмечаются явно.

Маршруты и DTO зафиксированы в [OpenAPI](design/a/openapi.json); backend использует
Python 3.12 и закреплённые зависимости. Выбор frontend-стека и передача интерфейсов
B1/B2 относятся к B0–B3. A4 должен собрать один общий worker B2+A3; отдельный
постоянный коллектор или scheduler внутри API этим планом не предусмотрен.
VPN и локальный helper рассматриваются как расширения после MVP.

## Уровни проверок

| Каталог | Назначение |
|---|---|
| `tests/unit/` | Уже реализованные каркас, реестр и сбор; будущие расписания и аналитика. |
| `tests/contract/` | Обработка ответов и ошибок Syncthing в адаптере. |
| `tests/integration/` | Backend, PostgreSQL и реальные тестовые экземпляры Syncthing. |
| `tests/e2e/` | Пользовательский сценарий от создания правила до подтверждённого результата в истории. |

В A0–A3 есть unit/contract, SQL и реальные интеграционные проверки. В A4 опубликован
[успешный CI ядра](https://github.com/danilsdk/syncthing-control-center/actions/runs/40376730151)
на head 5184ba2: 458 offline / 190 SQL / 9 core. Его результат не включает
будущие правила, UI, полный пользовательский E2E или VPS. Полный H0 validate на
принятой базе остаётся отдельным условием приёмки. Исторические журналы сохраняют
точные версии, результаты и ограничения каждого запуска.

## Harness разработки

H0 принят [PR #1](https://github.com/danilsdk/syncthing-control-center/pull/1)
28.10.2026. Coding agents используют карточки `.harness/tasks/`, отдельные
worktree, корневые/вложенные AGENTS.md и навыки `.agents/skills/`.
Границы обычного PR проверяются кодом и карточкой из принятой базовой ветки.
Harness относится к инфраструктуре разработки. Контракт приложения остаётся draft
до независимого review. Владельцы: A / playerboom — интеграция, данные, модели,
миграции и сборка; B / danilsdk — автоматизация, интерфейс и harness.

Подготовка A9 представлена отдельным PR поверх A0. Границы A0 не расширяются;
результаты и порядок приёмки записаны в [журнале A9](agent-log/a/A9.md).
