# Development harness

Harness задаёт воспроизводимый цикл работы coding agents. Оба участника используют
Codex: **B / danilsdk — автоматизация и интерфейс; A / playerboom — интеграция и данные**.
Harness поддерживает B, продуктовую инфраструктуру и БД — A.

## Что уже работает

- Корневые и вложенные `AGENTS.md`, repo skills `scc-task` и `scc-review`.
- 12 карточек MVP и H0 для настройки harness: точная ветка, разрешённые пути,
  зависимости, критерии готовности. Источник — `.harness/tasks/*.json`.
- Карта владельцев `.harness/project.json` и сформированный `CODEOWNERS`.
- Создание отдельного worktree без переключения исходной папки.
- Проверка committed, staged, unstaged и новых файлов; обе стороны rename.
- Локальные Git hooks, общий запуск проверок, CI и запрос review напарника.
- Раздельные журналы, шаблон передачи и стартовые запросы.

Приложение ещё не реализовано. Backend/Frontend-проверки становятся обязательными
при появлении компонента. Harness не объявляет неприменимые проверки успешными.

## Начальная настройка каждого участника

Сначала объедините PR с harness в main, затем обновите оба clone. Обычный Git
worktree не копирует незакоммиченные настройки из исходной папки.
Для harness нужны Git и Python 3.10+. Он не требует Python-пакетов.

```bash
python3 scripts/harness.py doctor
python3 scripts/harness.py install-hooks
python3 scripts/harness.py list
```

Git hooks устанавливаются только в локальную конфигурацию этого clone. Второй
участник делает установку в своём clone; настройка не переносится через Git.
Существующий сторонний hooksPath не перезаписывается. Его интеграция — отдельная
работа, остальные команды harness при этом доступны.

На Windows основные команды запускаются через установленный Python; вместо
`python3` допустим `python`. В Codex откройте проект из его Git-корня. Начните
новую сессию после обновления harness, чтобы навыки попали в каталог обнаружения.
До этого навыки можно читать напрямую по пути из `AGENTS.md`.

## Цикл задачи

1. Участник назначает одну карточку своему агенту. A получает A0–A5, B — B0–B5.
   Запуск задач координируется участниками через Issues/PR; registry не является
   распределённой блокировкой между компьютерами.
2. `start <ID>` обновляет origin и создаёт отдельную ветку/worktree. Две рабочие
   папки одного clone не могут использовать одну ветку одновременно.
3. Агент читает карточку, инструкции, контракт и доступные результаты зависимостей.
   Реализует критерии, затем запускает scope и validate.
4. Журнал записывается отдельным файлом своей задачи. Агент делает локальный commit
   только собственных изменений. По поручению участника отправляет ветку и PR.
5. Второй участник или отдельно назначенный агент делает review. Агент reviewer
   по умолчанию не редактирует код. Человек проверяет существенные ограничения.
6. Принимающий участник обновляет рабочую ветку относительно main, проверяет
   результат и объединяет PR. Следующая задача начинается от нового main.

Начать одновременно: твой агент — B0, агент друга — A0. B0 не зависит от
готового приложения. Зависимые задачи используют принятый контракт; пока он
не готов, допустимы только независимые исследования/прототипы с явным статусом.

```bash
# В твоём clone
python3 scripts/harness.py start B0

# В clone друга
python3 scripts/harness.py start A0
```

Команда выводит путь новой папки и запрос для агента. Откройте новую папку как
рабочую область Codex; создание Git worktree само по себе не создаёт чат в приложении.
В Codex можно также создать worktree средствами приложения и затем проверить
ветку/карточку в нём. Для уже существующей папки снимок начала создаётся один раз:

```bash
python3 scripts/harness.py snapshot B0
python3 scripts/harness.py prompt B0
```

`snapshot` сохраняет хеши уже существовавших чужих untracked-файлов в игнорируемую
локальную папку. Они не считаются изменениями агента, пока содержимое не изменилось.
Снимок не перезаписывается; он не исключает чужие staged или tracked-изменения.

## Команды

| Команда | Результат |
|---|---|
| `doctor` | Проверка структуры и доступности базовых инструментов |
| `list` / `show B1` | Карточки и точное разрешение задачи |
| `prompt B1` | Запрос для исполнителя |
| `start B1` | Отдельная папка/ветка из origin/main |
| `scope --task B1` | Все изменения задачи относительно main плюс рабочая папка |
| `scope --staged` | Только то, что попадёт в ближайший commit |
| `check` | Карточки, зависимости, CODEOWNERS, Python и ссылки документов |
| `self-test` | Проверки harness на временных Git-репозиториях |
| `setup` | Установка зависимостей уже появившихся компонентов |
| `validate --task B1` | Scope, структура, self-test и проверки приложения |
| `codeowners` | Обновление CODEOWNERS из карты владельцев |
| `install-hooks` | Включение локальных pre-commit/pre-push |

При offline-работе `start` допускает `--no-fetch`; исходную ветку можно явно
указать через `--base`. Перед публикацией всё равно проверяется актуальный main.
`scripts/validate.sh` — короткая оболочка над `validate` для macOS/Linux.

## Что проверяется и где границы защиты

`pre-commit` проверяет ветку и staged-пути. `pre-push` дополнительно проверяет
полную задачу и запускает проверки; не допускает прямой push в main, удаление
ветки или переписывание известной удалённой истории. Рабочие ветки обновляйте
через merge, не force push. Удалять объединённые ветки можно через обычный интерфейс
GitHub после приёмки, это не задача исполнителя.

CI использует правила карточки из базовой ветки для проверки diff: изменение
собственного allow в PR не расширяет разрешение этой проверки. При первом H0,
когда в main ещё нет harness, допускается только ветка `codex/h00-harness`.
Изменение harness, его CI и политики требует содержательного review человека.

Hooks и инструкции можно обойти; они не создают файловую sandbox и не гарантируют
отсутствие конфликтов между clone. Общая защита main, обязательные CI и approval
настраиваются отдельно в GitHub после первого опубликованного запуска.
`CODEOWNERS` требует write-доступа участников и не является запретом редактирования.

`review.yml` запрашивает review второго участника для готового PR. Он исполняет
только код принятой базовой ветки; исходники PR не запускаются с write-токеном.
Первый H0 проверяется вручную, пока harness отсутствует в main. Автоназначение
заработает после публикации и при наличии write-доступа у playerboom.

## Подключение проверки приложения

Конфигурации разделены, чтобы участники не меняли один файл одновременно:

- `.harness/checks/backend.json` — A: установка `backend[dev]` в `.venv`, Ruff,
  unit и contract pytest. A0 добавляет соответствующий `pyproject.toml` и проверки.
- `.harness/checks/frontend.json` — B: npm ci, lint, test:ci, build. B3 добавляет
  lock-файл и эти scripts либо меняет команды на выбранный менеджер.
- Реальный Docker/Syncthing E2E и VPS — отдельные проверки A4/B4. Их отсутствие
  в базовом CI не означает, что они выполнены. Результаты фиксируются в журнале.

`validate` сам не устанавливает пакеты и не обращается к реальным узлам.
`setup` — явная подготовка окружения; она не устанавливает пакеты глобально.
CI выполняет setup для существующих компонентов. Не выключайте проверку только
потому, что в рабочей папке не установлены зависимости.

## Контекст и продолжение работы

Используйте [шаблон результата](templates/agent-result.md). В журнале оставляйте
цель, важные решения, текущий diff, проверки, ограничения и следующий шаг.
Для продолжения в новом чате достаточно ID задачи, папки worktree, карточки и журнала.
Полные разговоры и ключи хранить в репозитории не нужно.

Новые задачи создаются отдельной JSON-карточкой с уникальным ID/веткой. В scope
разрешены `**` для дерева каталога и `*`/`?` для одного сегмента пути. `deny`
имеет приоритет. Не расширяйте существующую карточку ради прохода проверок:
сначала оформите порученное изменение границ и его review.
