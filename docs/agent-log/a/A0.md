## Существенные решения

- Регистрация использует connection_ref серверного allowlist; URL/ключ не передаются UI.
- Версия правила предотвращает потерю конкурентных изменений.
- Ручное resume имеет ключ повтора и проходит тот же механизм подтверждения.
- Начало отправки фиксируется commit до HTTP. Выбрана сеансовая advisory-блокировка:
  row lock внутри откатываемой транзакции потерял бы sent_at при падении после отправки.
- Семь таблиц учитывают сессию событий, историю удалённого правила и отдельные node-пробы.
- Подписанная cookie, CSRF и отказ в управлении до настройки защиты спроектированы,
  но их фактическая реализация относится к A2/A0.4.

## A0.3 — предметная схема и настоящая PostgreSQL

Добавлены семь типизированных SQLAlchemy-моделей, публичные импорты `app.models`,
Alembic environment/CLI и самостоятельная ревизия `a003_initial_schema`.
Миграция не импортирует изменяемые runtime-модели. Старт приложения по-прежнему
не создаёт таблиц и не применяет миграций. Серверный updated_at поддерживается
триггером, в том числе при raw SQL; UUID генерируется приложением.

Схема содержит составные FK папка/узел, RESTRICT для истории, SET NULL для
удалённого правила при сохранении JSON snapshot, частичные unique активного
правила/pending-команды/manual-ключа/позиции события. CHECK явно учитывают NULL
в подтверждении applied, признаки источника, порядок времени, scope снимков,
пары наблюдений, счётчики, дни и HH:MM. Payload ограничен разрешёнными ключами.

Встроенные проверки не подменяют будущие сервисы. Совпадение snapshot с правилом,
переходы статусов, IANA timezone, свежесть подтверждения и использование общих
блокировок реализуются в A0.4/B1/B2/A3. Атомарность событий/курсора здесь
проверена прямой транзакцией, коллектор A3 ещё отсутствует.

Воспроизведение — [a03-runbook.md](../../design/a/a03-runbook.md).
`check_postgres.py` создаёт собственный кластер с новым каталогом, случайным
паролем/SCRAM, свободным loopback-портом и только тестовой базой. Личные SCC/PG
настройки не наследуются. Существующая служба PostgreSQL и её данные не используются.
При успехе/ошибке теста свой сервер останавливается; при успешной остановке данные
удаляются, при неудаче остановки сохраняются для восстановления.

Фактическая среда: Windows, CPython 3.12.14, PostgreSQL **18.6** (server_version 180006).
Из песочницы Windows запуск PostgreSQL не смог создать restricted token;
реальный запуск выполнен под обычной учётной записью. Исправлены удержание pipe
дочерним сервером, кодировка вывода и размещение pytest-cache. Последний прогон
всего PostgreSQL-набора завершился без предупреждений; кластер остановлен и удалён.

## A0.4 — общие типы, блокировки и точки подключения

Добавлены все 30 публичных типов OpenAPI, enum и страницы. Проверяются форма,
неизвестные/лишние поля, UTC Z, IANA timezone, ISO-дни и HH:MM, семантика PATCH,
согласованность Execution/snapshot, node/folder-наблюдения и две метрики.
RulePatch.apply_to проверяет полное слияние; expected_version сверяет B1 под
блокировкой. ORM-значения дней/времени преобразуются общими helper-функциями.
Login.password и секреты NodeConnection исключены из repr/сериализации.

Реализованы Clock/SystemClock, внутренние наблюдения, SourceEvent/EventBatch,
SyncthingAdapter/AdapterFactory и безопасный AdapterError. Сессия источника
хешируется по исходной строке startTime без потери наносекунд. Ошибка записи
по умолчанию имеет исход unknown, её нельзя объявить отказом только по timeout.

AdvisoryLocks.folder использует стабильный ключ SHA-256 от внутреннего UUID.
LockLease.session привязана к удерживающему соединению; commit sent_at не снимает
сеансовую блокировку. После потери соединения lease не переподключается.
finally подтверждает unlock, а при ошибке исключает физическое соединение из pool.
Ошибка ограничения БД не подменяется ошибкой lock; вложенные сессии запрещены.

create_app принимает Clock/factory явно, выдаёт общие зависимости и закрывает
ресурсы. Защита require_admin по-прежнему запрещает управление до A2. DTO-ошибки
invalid_timezone/invalid_window/invalid_period и ошибки блокировки имеют безопасные
общие HTTP-ответы. Ошибки реально сериализуются через DTO Error.

Добавлена CLI-точка `python -m app.main worker` и run_worker для подключения A4.
Без B2 runtime/A1 factory CLI возвращает 2; реальный scheduler не имитируется.
При внедрённом runtime проверяется миграция и удерживается singleton lock другого
пространства ключей. Второй процесс возвращает 3 до вызова runtime; недоступность
БД/lock — 4, неожиданный отказ/ошибка закрытия — 1, успешное завершение — 0.
Ресурсы закрываются при ошибке и прерывании; сообщения не печатают upstream secrets.

Инструкция передачи: [a04-handoff.md](../../design/a/a04-handoff.md).
Рабочая логика и сетевой адаптер остаются A1/A2/A3/B1/B2/B4. B2 должен использовать
общие блокировки, проверять lease/context перед отправкой и версию/сессию при
подтверждении. Между БД и HTTP нет общей транзакции; helper не обещает доставки файла.
