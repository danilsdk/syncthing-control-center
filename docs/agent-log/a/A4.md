## Решения

- A4.2 — core PG/API/2 Syncthing с одноразовой миграцией и явным admin-create;
  можно выполнять до B1–B3, не выдавая за полный MVP.
- A4.3 — защищённые router, настоящий B1 evaluator и общий B2+A3 worker;
  A4.4 — UI B3/одна origin и CI; A4.5 — реальный system/E2E и review.
- Один image API/worker, Python 3.12, PG 18, Syncthing v2.1.7; конкретные
  registry tags/digests проверяются в A4.2. В A4.1 контейнерные версии не проверены.
- PG/Syncthing REST внутри закрытого стенда; host-порты только loopback для API/UI.
  Собственные volumes/project, без копирования ключей и home из нативного стенда.
- File secrets и bounded deploy entrypoint; не предполагать, что Settings уже
  поддерживает *_FILE. Реальный администратор создаётся вручную, без startup seed.
- Существующий run_worker/WorkerContext используется с singleton. Блокирующий
  run B2 не обеспечивает общий цикл A3 сам по себе; конечный шаг/hook согласовать
  с B2 до A4.3, не добавлять второй worker или API scheduler.
- Приёмка/база H0/A0/A1/A2/A3, D-01/B0 и поставка B1/B2/B3 ожидаются; полного
  harness validate в текущей базе нет. VPS — отдельное поручение.

unreferenced candidate для проверки дерева; ветка не переписывается. Это preflight
границ, не независимое review/approval. После merge требуется штатный полный
`validate --task A4`; hooksPath репозитория остаётся `.githooks`.

- `create_app` по умолчанию подключает events/snapshots, rules и executions под
  общей require_admin. Origin/CSRF применяются ко всем изменениям. Старые явные
  router из тестов потребителей учитываются без повторной регистрации.
- Реестр получает адаптацию ORM-правила к принятому вычислителю B1; desired state
  совпадает с расчётом исполнителя. DTO, модели, миграции и предметные модули A/B
  не менялись.
- [Runtime](../../../deploy/compose/image/runtime.py) вызывает A3 и конечный
  `reconciliation.service.run_once(context)` последовательно в одном процессе
  под существующим `run_worker`/singleton. Интервалы независимы, отсчёт — monotonic;
  B1/B2 каждый раз используют текущее UTC-время. В API scheduler не запускается.
- Guard действует перед каждым методом адаптера, каждым реальным транспортным
  HTTP-запросом, SQL и commit. Проверка самой singleton lease не рекурсирует.
  A3 может обработать ошибку внутри фазы, но последующие HTTP/SQL не разрешаются.
  SIGTERM запрещает новые операции, затем закрываются ресурсы и удаляются listeners.
- Общему launcher нужен pool минимум 3: singleton, folder lease и резолвер.
  Значение 2 отклоняется до создания ресурсов; обычные 5 сохранены. Общий hook A0
  не изменён: его прежний минимум 2 остаётся допустимым для иных injected factory.
- Обычный Compose up запускает API и worker. Ранние проверки ядра явно выполняются
  без worker, после них запускается настоящий общий worker. Полный core-check
  теперь требует 20 сценариев, включая восемь A4.3.
- SQL runner добавляет принятые B1/B2 suites отдельными процессами в собственную
  БД. У B-тестов нет маркера postgres: они запускаются полностью после A-наборов,
  а не попадают в offline-фазу с неявными skips. Форматирование B не менялось.

Три первых контейнерных прогона выявили ошибки нового тестового драйвера:
неверное имя snapshot-операции, старый CSRF после повторного входа и неподдержанный
GET отдельной папки. Драйвер приведён к существующим probe/OpenAPI/DTO, включая
idempotency_key ручной команды. Неуспешные прогоны не засчитаны, cleanup выполнен.

строгим JUnit gate; полный выбор B дал 228 реальных тестов без skips.
Отдельно воспроизведена гонка stop во время проверки lease: regression до fix
завершался failure, затем guard повторно проверяет stop перед началом I/O.
Итоговый review усилил guard до каждого транспортного HTTP и добавил pool preflight;
после этого 140 targeted и полный 20-сценарный Compose повторно прошли.
