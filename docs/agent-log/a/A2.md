## Получившееся поведение

Подготовлен [план A2](../../../backend/app/registry/README.md) с девятью операциями
существующего OpenAPI. В A2.2 реализованы три auth-маршрута и общая защита API,
локальный bootstrap администратора и безопасные ошибки. В A2.3 реализованы
остальные шесть операций реестра, серверный resolver и обновление наблюдений.

## Решения

- A2.2: один локально создаваемый администратор; подписанная сессия 8 часов,
  HttpOnly/SameSite/Secure, Origin/CSRF, ограничение входов; stdlib scrypt/HMAC
  без новой зависимости. Детали и первичные источники приведены в плане.
- A2.3: регистрация только через allowlist connection_ref после проверки источника,
  закрепление Device ID и атомарная запись узла/папок. Базовой схемы достаточно;
  новая миграция не потребовалась.
- Списки читают кеш, детальное чтение обновляет только выбранный enabled-узел
  по TTL. Ошибки сохраняют последние значения и времена, неизвестное не становится
  успехом. После регистрации A2 не меняет канонический checkpoint/курсор A3.
- Пара desired_paused/active_rule_id берётся только из авторитетного вычислителя
  B1; при активном правиле и отсутствии интеграции — безопасный отказ, не выдуманная цель.
- A2.4: настоящий API с частной PostgreSQL и двумя узлами, включая T-01/T-12,
  отказы и передачу следующим модулям. Scheduler/UI/коллектор не реализуются в A2.

## A2.2 — реализация авторизации

Поручение: «Следующий шаг — A2.2: реализация авторизации».
База подэтапа 15a2005af624bb46d87a93fc91994ae108642adc, исходное состояние чистое;
снимок a2-auth/A22-start.json вне репозитория. Ветка A2 сохранена; A0/A1/H0 не меняются.

### Реализация

- Явный локальный admin-create с getpass/подтверждением; без seed при старте API.
  Согласованный scrypt-профиль. Блокировка app_users сериализует bootstrap разных
  логинов; существующий администратор не перезаписывается. При двух пользователях
  SQL-хранилище закрывает auth вместо произвольного выбора первого.
- Login публичный, Origin проверяется до JSON/KDF. Me/logout и подключённые
  роутеры защищены require_admin. APIKeyCookie фиксирует adminSession в runtime
  OpenAPI; operationId/статусы/заголовки совпадают с design-контрактом.
- Cookie подписана отдельным HMAC-доменом, ограничена 2048 байт; payload — только
  user_id/expires_at/csrf_token. Дубликаты полей и неканонический base64url
  отвергаются; подпись проверяется до доверия данным. Срок 8 часов абсолютный;
  UUID/active пользователя перечитываются из БД на защищённом запросе.
- Origin/CSRF обязательны для изменений; повторённые заголовки отвергаются.
  Аутентификация выполняется до предметных зависимостей; fake router B и его
  адаптер не достигаются без доступа. Bearer не заменяет cookie.
- Один KDF одновременно, 5 попыток/мин на peer и 30/мин суммарно; bounded TTL
  память и монотонное время. Неизвестный login проходит dummy KDF; wrong/inactive
  дают одинаковую ошибку. SQL update после KDF повторно сверяет active/hash.
- Cookie HttpOnly/SameSite=Lax/Path=/, HTTPS/production — Secure. Logout удаляет
  её с теми же флагами. Серверный revoke-list не добавлен; ограничение stateless
  logout и отзыв через active/секрет явно описаны в плане.
- Общие Error/request_id, API no-store включая ошибки. CLI не печатает пароль,
  неизвестные аргументы или исключение закрытия БД. Реального администратора
  пользователя не создавали, действующие ключи не использовали.
- Новых зависимостей, миграций и смены общего wire-контракта нет.
  Auth-модули в registry/api соответствуют allow A2; код B не менялся.

## A2.3 — реестр узлов и папок

Поручение: «Следующий подэтап — A2.3: реестр узлов и папок».
База подэтапа 82f0ed190b8a593fcaf00e7acd14b2ab52a6379a, исходное состояние чистое;
снимок a2-registry/A23-start.json вне репозитория. Используется та же ветка A2.

### Реализация

- Шесть операций connections/nodes/folders подключены под общей защитой A2.2.
  Connections возвращает только публичный alias/name; серверные URL/ключи не
  принимаются от браузера. Сортировка, пагинация, DTO, operationId и статусы
  соответствуют существующему OpenAPI. PATCH меняет только name/enabled.
- NodeResolver получает соединение из серверной конфигурации по alias, перечитывает
  enabled/Device ID/checkpoint и передаёт их фабрике A1. create_app собирает фабрику
  по умолчанию при непустом наборе подключений и закрывает её при завершении.
- Регистрация проверяет identity и согласованность эпохи до/после полного списка
  конфигурации; сетевые обращения выполняются без занятого SQL-соединения.
  Одна транзакция создаёт узел/папки/checkpoint с cursor=0. Конкурентный дубликат
  откатывается с 409. Смена/удаление серверного alias во время проверки запрещает
  запись. Пустой корректный список папок допустим.
- Список узлов читает БД; карточка и папки обновляют выбранный enabled-узел по TTL.
  Короткая транзакция с блокировкой строки повторно сверяет состояние снимка.
  Конкурентное отключение, более новое наблюдение или запись курсора запрещают
  применение запоздалого ответа. Ошибка источника сохраняет прежние значения/времена;
  unknown runtime не становится idle/false/0.
- Исчезновение папки определяется полным успешным списком: present=false без
  удаления UUID/правил/истории. При возвращении UUID прежний. После регистрации
  GET/PATCH/refresh не меняют канонический checkpoint, включая ненулевой cursor.
- Проекция desired_paused/active_rule_id использует только внедрённый вычислитель
  B1; при активном правиле без него — 503. Зоны B и общий wire-контракт не менялись.
  Новых миграций/зависимостей нет, конфигурация настоящих Syncthing не изменялась.
