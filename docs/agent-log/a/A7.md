## Причина и исправление

Закреплённый Syncthing 2.1.7 запускает monitor и дочерний worker даже с
`--no-restart`. Стенд сохранял идентичность monitor. При потере shutdown API
его принудительное завершение могло оставлять worker, удерживающий home lock.
Нормальная остановка в первой диагностике завершила оба дочерних процесса;
во второй диагностике запрос shutdown намеренно отклонён тестовой обёрткой:
стенд сообщил running=[], но оба реальных worker оставались живы. Затем они
завершены только по заранее сохранённым PID, creation time и пути бинарника.
Эта диагностика воспроизводит дефект fallback; исторические сбои не объявляются
трассированными задним числом. Приватный отчёт: a1-review-ready/diagnose_monitor.json.

Только при serve очищенное окружение теперь явно задаёт STMONITORED=yes.
Это внутренний режим закреплённой версии, а не настройка пользовательского
Syncthing. Получается один непосредственно отслеживаемый worker на узел;
существующие проверки идентичности/владения и остановка применяются к нему.
CLI-пробы не получают STMONITORED. Чужие ST-переменные удаляются, process
environment пользователя не меняется. При обновлении Syncthing режим перепроверяют.

Основания: [main.go 2.1.7](https://github.com/syncthing/syncthing/blob/v2.1.7/cmd/syncthing/main.go#L283-L286)
и [monitor.go 2.1.7](https://github.com/syncthing/syncthing/blob/v2.1.7/cmd/syncthing/monitor.go#L110-L123).
Добавлена регрессия запуска через Popen с наследованными чужими ST-настройками.
Продуктовый адаптер, DTO, схема БД и алгоритм эпох в A7 не меняются.
