## Получившееся поведение

source_session_id обозначает эпоху доказанной непрерывности, а не гарантированно
уникальный ID запуска процесса. Сохранённый SourceCheckpoint содержит UUID узла,
raw startTime, ID эпохи и ориентир события: id, точное время, fingerprint
безопасного SourceEvent. Resolver передаёт checkpoint новому клиенту.

Адаптер читает status → доступное окно фиксированного /rest/events → status.
При совпадении startTime и ориентира он продолжает эпоху. При утрате доказательства
создаёт новую, учитывая предыдущую; отвергает старый курсор до since=0. Проверка
повторяется после long poll; пакет со сменившейся эпохой отвергается целиком.
Пустое исходное окно даёт retryable session_changed, без выдуманного ориентира.

SourceRestarted отмечает изменившийся startTime; SourceContinuityLost — потерю
доказательства при прежнем startTime. Последнее не объявляется доказанным
рестартом. Оба маркера локальные, с kind=restart и source_event_id=null.
Между недоказанными эпохами возможны повторы; ограниченный HistoryGap не выдумывается.

## Решения и изменения

Сравнение альтернатив и точная сериализация — в
[D-01, редакции 2](../../design/a/d01-stream-continuity.md).
Один startTime непригоден из-за секундной точности. Windows process_start_time
в /metrics также оказался секундным; CSRF-токены сохраняются в БД источника.
Один начальный Starting исчезает из ограниченного буфера. Отдельный sidecar
boot UUID усложняет установку на каждом узле. Для MVP выбран проверяемый
сохраняемый ориентир и консервативная граница при утрате доказательства.

Обновлены внутренние DTO, адаптер и factory, семантика общего Event,
ManagedNode.source_stream_anchor и отдельная миграция a101_stream_anchor.
Старые миграции не редактировались. Публичная форма JSON Event не изменилась:
event_type уже строка; SourceContinuityLost допустим с прежним kind=restart.
OpenAPI и примеры публичных полей не потребовали смены структуры.

Миграция сохраняет старые события, сессии и курсоры; legacy anchor=null не
считается доказательством. Downgrade разрешён на legacy/пустом состоянии, но
отказывается удалять уже появившиеся ориентиры или неопределённые границы.
Проверена атомарность отказавшего downgrade и записи события/курсора/checkpoint.
На рабочих БД миграция не запускалась.

Для будущего A3: под блокировкой строки узла записывать границу, события,
source_session_id, raw startTime, anchor и курсор одной транзакцией. Для A2:
восстанавливать checkpoint в resolver. Для B2: смена эпохи отменяет прежнее
подтверждение. Эти потребители в D01 не реализованы и не изменены.

Реальный прогон: **2026-10-25 01:08:06–01:08:49 по Москве**. В
[обезличенном отчёте](../../../tests/integration/syncthing_adapter/evidence-d01-v2.1.7.json):

- Отдельный процесс Python загрузил checkpoint с диска и сохранил эпоху;
  процессы Syncthing не перезапускались.
- После настоящего рестарта поток достиг id=18 при старом ориентире 15.
  Тестовый транспорт удерживал status.startTime и uptime прежними, не меняя
  реальные события. Старый курсор отвергнут, эпоха сменилась, чтение началось с 1.
- Нативные старты фактически были в 01:08:27 и 01:08:39. Настоящий restart
  в одну секунду не заявляется; коллизия полей воспроизведена транспортом.
- Pause/resume повторён; изменялось только paused, остальные папки сохранены,
  requiresRestart=false; после resume переданы все 63 байта тестового файла.
- Оба собственных процесса остановлены; running пуст. API-ключи и runtime
  исключены из Git; публичный отчёт содержит только разрешённые поля.

Во время промежуточных Windows-прогонов наблюдались занятый порт, задержка
снятия lock источника и ограничения запуска/инвентаризации внутри sandbox.
Добавлено конечное ожидание освобождения своих портов после собственной
остановки. Чужие процессы не завершаются. Итоговые PostgreSQL и Syncthing
проверки прошли в обычном пользовательском контексте после автоматического
разрешения запуска вне sandbox; они не требовали прав администратора.
Временный PostgreSQL остановлен и удалён; рабочая служба не затрагивалась.
