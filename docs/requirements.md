# Рабочие требования MVP

Документ основан на [исходном плане проекта](../syncthing_coursework_mvp_plan.md).
Ниже приведены критерии полного MVP. Часть уже реализована в опубликованных A0–A4;
статус реализации и независимой приёмки указан в [README](../README.md) и
[архитектуре](architecture.md). План не является утверждённым преподавателем ТЗ.

## Цель и объём

Разработать систему централизованного наблюдения за экземплярами Syncthing, управления синхронизацией по расписанию и анализа истории. Демонстрационный стенд: два экземпляра Syncthing, одна–две тестовые папки, один администратор.

## Функциональные требования

| ID | Планируемый сценарий | Критерий приёмки |
|---|---|---|
| F-01 | Регистрация экземпляра Syncthing | Экземпляр добавлен; подключение к API проверено через доверенный канал. |
| F-02 | Просмотр узлов и папок | Панель показывает конфигурацию и доступное наблюдаемое состояние. |
| F-03 | Индикация проблем | Недоступность узла, пауза папки, ошибка и неизвестное состояние различаются. |
| F-04 | Расписания синхронизации | Для пары «экземпляр — папка» задаются дни, временное окно и часовой пояс; допускается одно активное правило. |
| F-05 | Выполнение правила | Желаемое значение `paused` применяется через адаптер и подтверждается повторной проверкой. |
| F-06 | Восстановление после отключения | После восстановления связи вычисляется состояние на текущий момент и проверяется его применение. |
| F-07 | История | События и попытки выполнения команд сохраняются с временем, объектом и результатом. |
| F-08 | Аналитика | Рассчитываются минимум два показателя по сохранённым данным и отображаются за выбранный период. |
| F-09 | Авторизация | Управление доступно только авторизованному администратору. |
| F-10 | Проверка и развёртывание | Есть автоматические проверки, воспроизводимый стенд Docker Compose и демонстрация на VPS. |

## Основные ограничения

- Центральный сервер хранит служебные данные; содержимое файлов передаёт Syncthing.
- Ответ HTTP `200` не заменяет проверку фактического применения команды.
- После перезапуска или возвращения узла сначала рассчитывается актуальное желаемое состояние.
- Неизвестные состояния и пропуски наблюдений не учитываются как подтверждённый успех.
- Временные отметки истории хранятся в UTC, расписания учитывают часовой пояс IANA.
- API Syncthing доступен только через закрытую сеть или защищённый канал; API-ключи не передаются в браузер.
- Для испытаний используются отдельные демонстрационные файлы, секреты не публикуются в репозитории и журналах.

## Готовность MVP

Полная цепочка должна работать на реальном стенде: чтение состояния → расчёт правила → применение → подтверждение → запись в БД → отображение в панели. Дополнительно проверяются потеря и восстановление связи, авторизация, корректность истории и аналитики.

Подробные сценарии T-01–T-13 и условия завершения курсовой приведены в разделах
12–13 исходного плана. Фактические результаты фиксируются в журналах A0–A4
и доказательствах соответствующих PR. Успешные проверки ядра не подтверждают
готовность расписаний B1, исполнителя B2, интерфейса B3, аналитики B4 и полного MVP.
