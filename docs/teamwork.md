# Совместная работа двух участников

Распределение подтверждено участниками: **B / danilsdk — ты, автоматизация и
интерфейс; A / playerboom — друг, интеграция и данные**. Буквы и ID задач
сохранены, роли участников изменены. Процесс разработки опирается на
[development harness](harness.md); точные границы карточек — `.harness/tasks/`.

## 1. Один репозиторий, отдельные рабочие копии

Оба участника используют `https://github.com/danilsdk/syncthing-control-center`,
свои учётные записи GitHub и свои локальные clone. Владельцу репозитория нужно
предоставить напарнику доступ к записи, если его ещё нет.

Каждая задача идёт в отдельной короткой ветке. Постоянные ветки «весь backend»
и «весь frontend» не нужны: их трудно регулярно объединять.

```text
main
 ├─ codex/a01-adapter       → PR → review B → main
 ├─ codex/b01-scheduling    → PR → review A → main
 └─ codex/b03-frontend      → PR → review A → main
```

Коммиты и push в разные ветки можно делать одновременно. Слияния PR выполняются
по очереди с проверкой на актуальном `main`. Разные ветки не исключают конфликтов
в одних файлах и ошибок на стыке модулей; для этого нужны владельцы и контракты.

Для одного агента в отдельном clone:

```bash
git fetch origin
git switch -c codex/a01-adapter origin/main
```

Если в одной рабочей папке уже есть работа, её не переключают и не сбрасывают.
Для дополнительного параллельного агента создают отдельный worktree, например:

```bash
git fetch origin
git worktree add ../scc-a01 -b codex/a01-adapter origin/main
git worktree add ../scc-a03 -b codex/a03-collection origin/main
```

Эти примеры — альтернативы: одну ветку не создают повторно. Каждый агент получает
путь именно своего worktree. Начните с одного исполняющего агента на участника;
дополнительных подключайте только к независимым задачам с непересекающимися путями.

## 2. Владельцы файлов

Владелец отвечает за реализацию и целостность зоны. Второй участник читает и
проверяет её, а изменения предлагает отдельной задачей. Владение — соглашение
команды, само по себе оно не блокирует запись средствами Git.

Ниже точное правило имеет приоритет над общим. Новые пути внутри зоны наследуют
её владельца. Новый путь вне перечисленных зон сначала назначают владельцу.

| Зона | Владелец | Содержание |
|---|---|---|
| `backend/app/syncthing_adapter/` | A | Весь доступ к Syncthing |
| `backend/app/registry/` | A | Узлы и папки |
| `backend/app/collection/` | A | События, снимки, восстановление наблюдений |
| `backend/app/models/`, `backend/migrations/` | A | Вся общая схема БД и миграции |
| `backend/app/contracts/` | A | Общие DTO и интерфейсы; каталог создаётся в A0 |
| `backend/app/main.py`, `backend/app/db.py`, `backend/app/config.py` | A | Сборка приложения и общая конфигурация |
| Остальные общие файлы в `backend/` | A | Backend-зависимости, общий код, сборка |
| `backend/app/api/` | A, кроме следующих трёх файлов | Авторизация, зависимости, узлы, папки, события, подключение роутеров |
| `backend/app/api/rules.py` | B | Роутер правил |
| `backend/app/api/executions.py` | B | Роутер истории команд |
| `backend/app/api/analytics.py` | B | Роутер аналитики |
| `backend/app/scheduling/` | B | Валидация правил и расчёт желаемого состояния |
| `backend/app/reconciliation/` | B | Исполнение, подтверждение и история команд |
| `backend/app/analytics/` | B | Формулы и запросы показателей |
| `frontend/` | B | Весь интерфейс, его зависимости и lock-файл |
| `tests/` | A, кроме следующих строк | Общие фикстуры, адаптер, реестр, сбор данных, системные проверки |
| `tests/unit/scheduling/`, `tests/unit/reconciliation/`, `tests/unit/analytics/` | B | Unit-проверки B |
| `tests/integration/rules/`, `tests/integration/executions/`, `tests/integration/analytics/` | B | Интеграционные проверки B |
| `tests/e2e/ui/` | B | Пользовательские сценарии |
| `deploy/`, продуктовые `scripts/`, CI приложения, корневые конфигурации | A | Стенд и продуктовая инфраструктура |
| `.harness/`, `.agents/`, `.githooks/`, `scripts/harness.py`, `scripts/validate.sh`, `scripts/tests/` | B | Harness, навыки и его проверки |
| `.harness/checks/backend.json` | A | Точные backend-проверки |
| `.github/workflows/harness.yml`, `review.yml`, CODEOWNERS и шаблоны | B | Проверки процесса и правила review |
| `README.md`, исходный план, продуктовые документы `docs/` | A | Общий вход и продуктовые решения |
| `AGENTS.md`, `docs/harness.md`, `docs/teamwork.md`, `docs/agent-tasks.md`, промпты и шаблоны | B | Инструкции процесса агентской разработки |
| `.harness/tasks/<ID>.json` и собственный журнал | Роль задачи | Отдельная карточка и результат; изменение границ требует review |
| `docs/design/b/`, `docs/report/parts/b/`, `docs/agent-log/b/` | B | Проектирование B, вклад в отчёт и журналы его агентов |
| `docs/design/a/`, `docs/report/parts/a/`, `docs/agent-log/a/` | A | Проектирование A, вклад в отчёт и журналы его агентов |

`models/__init__.py`, `api/__init__.py`, общие тестовые фикстуры и общий lock-файл
backend редактирует A. B реализует операции со своими данными в своих пакетах,
используя модели A. Миграции для B делает A по согласованному описанию.
Это исключает параллельное создание несовместимых голов Alembic.

Финальный `.docx` собирает A из отдельных частей отчёта. B передаёт текст и
рисунки своей части через `docs/report/parts/b/`. Оба участника проверяют итоговый
документ; одновременно редактировать один Word-файл через Git не следует.

## 3. Контракты до параллельной реализации

A0 заменяет начальный draft `docs/contracts.md` согласованным контрактом и готовит общие модели/интерфейсы. B0
проверяет их по своим сценариям. Только после принятия этого PR зависимые задачи
опираются на контракт. Ниже — список решений, а не уже реализованный API.

| Что зафиксировать | Зачем |
|---|---|
| ID узла, ID записи папки и Syncthing Folder ID | Не смешивать глобальные ID приложения с ID внутри экземпляра |
| Схема всех семи таблиц из плана | B начинает расписания и историю без изменения общей схемы |
| Интерфейс адаптера: чтение, установка паузы, проверка, события и ошибки | B тестирует исполнитель на подмене, A реализует настоящую интеграцию |
| DTO узлов, папок, правил, событий, команд, аналитики | UI и backend используют одинаковые поля |
| Маршруты и JSON-примеры, ошибки, фильтры, пагинация | Интерфейс может работать на mock-данных до готовности API |
| Авторизация и получение текущего пользователя | Роутеры B используют общую защиту A |
| Формат UTC, IANA timezone, нумерация дней недели | Исключить разные трактовки времени |
| Окно через полночь, равные границы, DST, выключенное правило | Одинаковое поведение движка и формы UI |
| Состояния команды и переходы между ними | HTTP-успех не превращается в ложное подтверждение |
| Источники истории и формулы метрик | Коллектор A сохраняет данные, достаточные для аналитики B |
| Кто запускает worker и как обеспечен один исполнитель | A собирает приложение, B реализует цикл работы |

A0 оставляет frontend-фреймворк на выбор B: frontend живёт отдельно, а A включает
его воспроизводимую сборку в стенд после B0/B3. Не разрабатывайте одновременно
два варианта одного интерфейса.

После принятия контракта изменения оформляют маленьким PR владельца A. В нём
должны быть пример данных, затронутые потребители и порядок перехода. Если API
ещё не готов, агент B использует согласованные fake/fixture, явно обозначая это
в результатах. Не копирует адаптер и не придумывает второй контракт.

## 4. Порядок работ и баланс

Полные задания: `docs/agent-tasks.md`. Настройка harness H0 подготовлена отдельно и не входит в оценки будущих продуктовых задач. Оценки ниже — первоначальные относительные
оценки сложности, не часы и не гарантия срока. После двух первых PR сравните
фактические затраты и пересмотрите следующие задачи.

| Этап | A: интеграция и данные | Оценка | B: автоматизация и интерфейс | Оценка |
|---|---|---:|---|---:|
| Подготовка | A0: каркас, схема, контракты | 5 | B0: сценарии, проверка контракта, план UI | 3 |
| Основа | A1: адаптер и проверка реального API | 5 | B1: расписания и API правил | 5 |
| Управление | A2: реестр, CRUD, авторизация | 5 | B2: исполнитель и история команд | 8 |
| Наблюдение / UI | A3: события и snapshots | 5 | B3: веб-панель | 5 |
| Готовность | A4: стенд, CI, общая интеграция | 5 | B4: аналитика и пользовательские E2E | 5 |
| Защита | A5: материалы интеграции, сборка отчёта | 2 | B5: материалы автоматизации, сценарий защиты | 2 |
| **Всего ориентировочно** | | **27** | | **28** |

У обоих есть самостоятельная серверная логика, тесты и вклад в отчёт. A получает
больше общей инфраструктуры, B — сложный исполнитель и весь UI. Если одна зона
окажется тяжелее, передавайте целую ещё не начатую карточку вместе с путями.
Число файлов, коммитов и строк кода не используется как мера равенства вклада.

Порядок зависимостей:

1. A0 и B0 стартуют одновременно. B0 не меняет общие контракты в своей ветке.
2. После A0 параллельно идут A1 и B1. B1 работает с моделями и тестовыми подменами.
3. A2, A3 и B2 используют результат A1; первые unit-проверки B2 возможны раньше.
4. B3 начинает UI на JSON-примерах после A0, затем подключает реальные A2/B1/B2.
5. B4 согласовывает формулы в B0, реализует их после A3/B2. A4 сдаёт основной
   стенд после A2/A3/B1/B2/B3; затем B4 проводит на нём пользовательский E2E.
6. A5/B5 ведут материалы по мере работы; реальные результаты дополняются после A4/B4.

Один участник может выполнять карточки последовательно. Параллельные агенты
одного участника используют отдельные worktree и уточнённые пути: например,
A2 и A3 не должны одновременно изменять модели, миграции или общий журнал.

## 5. Карточки и pull request

Ведите один список задач: достаточно GitHub Issues с состояниями «запланировано»,
«в работе», «на проверке», «готово». Владелец обновляет свою карточку. Начать с
A0–A5 и B0–B5; крупные B2/B3 можно разбить на небольшие PR без смены владельца.

Каждая карточка содержит ID, одного исполнителя, разрешённые пути, зависимости,
критерии готовности и проверки. Не запускайте двух агентов на одну карточку.
Если задача заблокирована чужим интерфейсом, отдельно опишите нужное изменение
и продолжайте работу, которую позволяет существующий контракт.

В PR укажите:

- ID и требование F-xx;
- что теперь работает;
- какие файлы изменены и не вышли ли они за границы задачи;
- проверки и фактические результаты;
- изменения контрактов/схемы и ограничения, если они есть.

Другой участник проверяет PR. Для общих контрактов и изменения конфигурации
Syncthing особенно важен review обоих участников. Перед merge обновите рабочую
ветку через merge актуального `origin/main`, при необходимости исправьте
конфликты и проверьте итог. После merge начинайте следующую задачу от нового `main`.

## 6. Настройки GitHub

Когда опубликован первый CI, настройте для `main` требование PR, одного approval
и успешных обязательных проверок. Включите запрет обхода правил, если он доступен
для вашей конфигурации. Доступность защиты зависит от типа репозитория и тарифа;
до настройки команда соблюдает эти правила организационно.

Карта уже перенесена в `.github/CODEOWNERS` для `playerboom` и `danilsdk`.
Файл генерируется из `.harness/project.json` командой `codeowners`. Он назначает
владельцев для review; не запрещает редактировать файлы и не заменяет AGENTS.md.
Review своей задачи выполняет второй участник, даже если её CODEOWNER — сам автор.
После принятия harness `review.yml` автоматически запрашивает review напарника
для готового PR по роли его карточки; draft PR ждёт перевода в ready.
Для общей зоны не рассчитывайте, что два владельца в CODEOWNERS автоматически
означают два обязательных approval: review второго участника контролируется отдельно.

Эти документы не меняют доступы GitHub, защиту ветки или состояние удалённого
репозитория. Настройки и приглашения применяются отдельными действиями владельца.

## Первые действия

1. Убедиться, что playerboom имеет write-доступ к репозиторию.
2. Опубликовать harness из `codex/h00-harness` одним PR и объединить после review.
3. Обновить оба clone и включить hooks по `docs/harness.md`.
4. Твоему агенту передать [B0](prompts/start-b.md), агенту друга — [A0](prompts/start-a.md).
5. Принять общий контракт и перейти к A1/B1 в отдельных worktree.
