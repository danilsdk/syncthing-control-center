# Задания агентам двух участников

Участники: B / danilsdk (автоматизация и интерфейс) и A / playerboom (интеграция
и данные). Пакеты ниже задают обязанности и критерии приёмки; фактические
результаты находятся в журналах задач и PR. Одна карточка — один владелец,
но крупный пакет можно сдавать несколькими небольшими PR.

Перед задачей используйте `python3 scripts/harness.py prompt ID` и `$scc-task`.
Точные пути в `.harness/tasks/ID.json` имеют приоритет над кратким перечнем ниже.
Собственный журнал и JSON-карточка входят в область задачи; расширение границ
не выполняется попутно. Текст ниже объясняет предметный результат.
Если несколько агентов работают одновременно, уточняйте непересекающиеся пути
внутри этой границы и давайте каждому отдельный worktree.

## Порядок A3, A10, B6 и A4

Целевая платформа — macOS 26.1 на Apple Silicon (ARM64) с Python 3.12 и
Syncthing 2.1.7. План актуализирован 13.11.2026 после принятия A3 и B3.
Нативное окружение проверяет A10, Docker Desktop входит в приёмку A4.

| Этап одним запросом исполнителю | Владелец | Условие и результат |
|---|---|---|
| План и карточки A10/B6 | Подготовка A, публикация B / danilsdk, приёмка A | Принять отдельный PR H0 в `main` до веток реализации. |
| A3: коллектор и API истории | A / playerboom | Принят в `main` в [PR #6](https://github.com/danilsdk/syncthing-control-center/pull/6). Его Mac-сценарии входят в приёмку A10 и CI B6. |
| A10: загрузка, процессы, тесты, инструкция и PR | A / playerboom | После принятия карточки, от актуального `main` с A0/A1/A2. |
| A10: реальный Mac и независимая приёмка | B / danilsdk | Python 3.12 ARM64, macOS 26.1, PostgreSQL, два Syncthing и коллектор A3. До слияния нужно подтверждение изменений demo config ответственным участником. |
| B6: вся матрица CI и PR | B / danilsdk, приёмка A | После принятия A10, от актуального `main`. |
| A4: общая интеграция и ARM64 Compose | A, UI и аналитика B | Полная приёмка после A10, B6 и остальных зависимостей A4. Независимые части A4 можно готовить заранее. |

Загрузчик, управление процессами и регрессии входят в одну реализацию A10.
Формальные зависимости карточек указаны в `depends_on`. Совместный прогон
коллектора на Mac проводится на актуальной базе с принятым A3.

### A10. Нативная совместимость с macOS ARM64

**Зависимости:** принятые A0/A1/A2 и сама карточка в main. Ветка

`tests/integration/syncthing_adapter/`; инструкция
`docs/design/a/macos-development.md` и собственный журнал. API, модели,
зависимости backend, Compose, CI и harness в реализацию A10 не входят.

**Сделать одним запросом:**

- Разделить ОС, архитектуру, формат архива и имя исполняемого файла. Добавить
  официальный macOS ARM64 ZIP Syncthing 2.1.7 с проверенным SHA-256: внутри
  `syncthing`, а не Windows `syncthing.exe`. Сохранить ограничения скачивания,
  безопасное извлечение и прежние Windows/Linux. Rosetta и несовместимую
  архитектуру Python диагностировать явно, не выдавая эмуляцию за ARM64-прогон.
- Реализовать Mac-проверку принадлежности процесса по PID, времени старта и
  исполняемому файлу средствами ОС. `/proc` и `pidfd` относятся к Linux.
  Сначала проверять принадлежность, затем выполнять аутентифицированный HTTP
  shutdown. При недоступном shutdown — ограниченная по времени ошибка и
  сохранённый runtime; запрещены сигнал по одному PID, ложный cleanup и
  удаление каталога работающего процесса. Прежние безопасные Windows/Linux
  механизмы сохранить.
- Исправить причины трёх прежних Mac-отказов в `test_bench.py`:
  `test_bad_release_digest_cannot_extract_an_executable`,
  `test_stale_process_identity_never_sends_shutdown_or_terminates`,
  `test_even_matching_pid_outside_runtime_cannot_be_stopped`.
  Добавить регрессии выбора платформы, архива и принадлежности процесса.
  Не скрывать дефекты skip/xfail и не ослаблять проверки чужого процесса.
- Подготовить инструкцию чистой установки Python 3.12 ARM64, PostgreSQL и двух
  собственных Syncthing; команды установки зависимостей, validate, миграций,
  SQL/API-проверок A1/A2, запуска/остановки и восстановления конфигурации.
  Ключи и локальные пути не включать в Git/логи. Новые runtime-зависимости не
  планируются; необходимость изменения pins или чужих модулей — отдельная
  задача с явно согласованными границами.
- Выполнить доступные Windows/Linux-проверки, передать один PR с результатами
  B для реального Mac-прогона. Не называть тестовые doubles доказательством
  запуска на Mac. Исправления и повторные проверки остаются в том же A10.

**Готово, когда:** B воспроизвёл чистую установку на macOS 26.1 ARM64, полный
validate, применимые SQL/API-сценарии на настоящем PostgreSQL и двух Syncthing,
передачу файлов с проверкой содержимого, pause/resume, restart, restoration и

регрессируют. На той же базе с принятым A3 проверяется работа коллектора на Mac.

### B6. Обязательный CI платформ

**Зависимости:** H0 и принятый A10. Ветка
`codex/b06-platform-ci` — отдельный PR от свежего main, проверяет A / playerboom.

**Пути:** точный перечень в [.harness/tasks/B6.json](../.harness/tasks/B6.json).
`.github/workflows/harness.yml`, конкретный helper `scripts/check_platform.py`
и его `scripts/tests/test_check_platform.py`, `docs/harness.md`, собственная
карточка и журнал. Общий код harness, политика merge, роли и продуктовые модули
не меняются ради зелёного результата.

**Сделать одним запросом:** матрица Python 3.12 на Windows amd64, Linux amd64
и macOS ARM64; нативная Mac-интеграция с PostgreSQL и двумя Syncthing по A10;
отчёты с фактическими версиями/архитектурой, кодами завершения и cleanup.
Для Mac использовать ARM64 runner (ориентир `macos-26`); он не закрепляет
patch 26.1 и не заменяет приёмочный прогон на Mac напарника. Не рассчитывать
на Docker Desktop или вложенную виртуализацию hosted Mac: контейнерный E2E
остаётся A4, а нативные проверки запускаются без Docker.

Сохранить стабильный обязательный `validate` как итог всех обязательных
платформ и Mac-интеграции: падение, отмена и неожиданный skip должны блокировать
его успех. Не применять `continue-on-error`, искусственные skip/xfail или
скрытие Mac за необязательным check. Сохранить чтение доверенного harness и
границ из принятой базы, неизменные роли и независимое review. При добавлении
helper проверить реальные отказные условия и завершение дочерних процессов.

**Готово, когда:** текущий head PR получил все обязательные прогоны, отчёты
позволяют повторить их локально, а дефект Mac-проверки блокирует итоговый gate.
Нативная интеграция включает сценарии коллектора принятого A3. Compose
принимается в A4, полный пользовательский сценарий и аналитика — в B4.

## Как передать карточку агенту

Подготовьте отдельный worktree командой `start ID` после публикации harness.
Передайте выведенный запрос агенту в новой рабочей папке. Для текущего worktree
используйте `prompt ID`; полный процесс — [harness](harness.md).

Готовые первые задания:

- [Твоему агенту — B0 / danilsdk](prompts/start-b.md).
- [Агенту друга — A0 / playerboom](prompts/start-a.md).

Публикация поручена в этих стартовых запросах: агент делает commit, push своей
ветки и PR, агент напарника проверяет и при готовности объединяет результат
по постоянному поручению AGENTS.md. Локальный вызов `prompt` сам по
себе не добавляет разрешение push, если участник ещё не поручил публикацию.

Для отдельно назначенного reviewer используйте `$scc-review` и ID карточки.
Попросите читать полный diff и журнал без изменения кода. Журнал каждой задачи
оформляется по [шаблону результата](templates/agent-result.md).
