после реальной интеграции; core нельзя назвать завершённым MVP. Файл — compose.yaml,
отдельное имя проекта scc-a4-dev; без container_name и общих host home. Native
runtime других checkout и рабочая PostgreSQL не переиспользуются.

Runtime: Python 3.12 согласно pyproject; PostgreSQL 18 и Syncthing v2.1.7 для
согласованности с локальными проверками. В A4.2 проверить наличие официальных
образов и закрепить точные tag/digest/архитектуру, Python patch и PG minor.
Наличие или работоспособность этих контейнерных образов в A4.1 не проверялись.
latest не использовать. Если pinned Syncthing образ недоступен, решение о
сборке из проверенного архива/версии оформить явно до запуска, без тихой замены.

API и worker используют один backend image, установку из зафиксированных
requirements и явные разные команды. Runtime под непривилегированным пользователем,
когда это допускают образ и права volumes. Для данных PG/demo home — отдельные
именованные volumes проекта; системные испытания создают собственный project name.

## Сеть и секреты

Внутренняя bridge-сеть изолирует PG и REST Syncthing; их порты по умолчанию не
публикуются на хост. GUI demo-узлов — только при явном debug-профиле и bind
127.0.0.1. Отключены discovery, relay, NAT, автообновление и отправка диагностики;
узлы знают только статический адрес своего peer внутри стенда. Демонстрационным
узлам иные сети/папки не добавляются. Центральное приложение хранит служебные
данные, не содержимое файлов. API использует private и отдельную api_access для
публикации loopback-порта; PG/Syncthing подключены только к private.

На раннем стенде API доступен на 127.0.0.1:8000. После B3 UI на 127.0.0.1:8080
проксирует /api к api:8000, создавая одну browser origin; allowed_origins задаётся
явно под эти адреса без wildcard. Syncthing API-ключи не выдаются UI. VPS/HTTPS
будет отдельной конфигурацией с реальным доменом, Secure cookie и закрытой БД.

Действующие ключи, DB password и session secret создаются локально в новом
ignored deploy/compose/runtime/private и передаются через Compose secrets только
нужным сервисам. В Git — схема/публичные placeholders, без постоянного общего
пароля. Secrets являются локальными файлами, их резервирование и доступ оператора
нужно описать; Compose не объявляется внешним хранилищем секретов.

Текущий Settings принимает значения SCC_* из окружения, поддержки произвольных
*_FILE нет. В A4.2 нужен явный entrypoint в deploy/, который прочитает только
согласованные bounded secret-файлы и создаст Settings/окружение собственного
процесса без вывода значений. Не считать *_FILE уже реализованным контрактом.
Не помещать секреты в build ARG/образ/CLI, вывод compose config или CI artifacts.
Для синтаксической проверки Compose использовать тихий режим, не печатать
развёрнутую конфигурацию. Ключи закрепляются за новыми demo home; init должен
отказываться перезаписывать чужой или непомеченный каталог.

## Запуск и восстановление

1. Проверить Docker daemon, Compose, Linux containers, свободные loopback-порты
   и принадлежность только собственных каталогов/volumes. На Windows для этого
   проекта выбран Docker Desktop с WSL 2; для A4.1 установка не требовалась.
2. Явно подготовить приватные настройки и demo config. Повтор без изменения
   параметров сохраняет ключи, Device ID и данные; чужой runtime не принимается.
3. Запустить PG и дождаться healthcheck. migrate зависит от service_healthy;
   API/worker — от успешного завершения migrate. Состояние running само по себе
   не является доказательством готовности.
4. Дождаться собственного API readiness и двух реальных Syncthing REST; проверка
   закреплённых identity при регистрации выполняется production адаптером.
5. Оператор явно запускает app.registry admin-create --login admin в интерактивной
   сессии, вводя пароль через getpass. Без bootstrap login закрыт; автоматический
   seed при startup не добавляется. Demo-узлы регистрируются через защищённый API.
6. После готовности B включить общий worker и UI, проверить основной сценарий.
   Наблюдения, история и правила переживают обычный restart/down без удаления volumes.
7. Обычная остановка сохраняет данные. Сброс данных — отдельная явная операция
   только для подтверждённого собственного тестового project, без общего prune.

Миграции не откатываются автоматически при restart. При недоступной БД/миграции
readiness неуспешен, worker не начинает внешние записи. После возврата источника
применяется желаемое состояние на текущий момент, старая очередь не проигрывается.
Длительные ожидания ограничены deadline, подтверждения — повторными наблюдениями,
а не фиксированным sleep или только HTTP 200.

## Общий worker и граница B2

Использовать существующие run_worker/WorkerContext и advisory singleton. Один
процесс владеет циклом, API lifespan не запускает фонового исполнителя.
Фабрика адаптера и SQL resources закрываются при завершении; lock проверяется
через context.ensure_active() до цикла и перед внешней записью.

Управление B2 и наблюдения A3 имеют интервалы 15/30 секунд из текущих Settings;
due-отбор A3 остаётся внутри collect_once. Вторая копия worker отвергается общей
блокировкой даже при запуске из другого контейнера с той же БД. Ошибка одного
узла не должна останавливать обслуживание другого или выдумывать измерения.

До A4.3 согласовать с B2 конечный вызов одного прохода или явный hook коллектора
в принадлежащем B2 цикле. Существующий WorkerRuntime.run(context) — блокирующий
вход, его нельзя просто выполнить перед бесконечным вторым циклом A3. Имя нового
метода B2 пока не определено и не предполагается. Не решать это вторым worker
или самостоятельным scheduler в API. Folder locks перед внешними командами
продолжают использоваться B1/B2 через общий механизм A0.

API A4 подключает router A3/B1/B2 под имеющуюся require_admin. Для desired state
в ответах A2 передаётся настоящий вычислитель B1; отсутствие зависимости не
заменяется выдуманным desired_paused. OpenAPI/DTO не меняются скрыто при wiring.

API дополнительно использует api_access: Docker 29.9.2 не создал эффективную
публикацию порта при единственной internal-сети. PG/Syncthing остаются только

Включение через штатный SetupAPI DICS_ENABLE / DICS_FLAG_CONFIGSPECIFIC сняло
этот флаг: статус OK / Code 0, отдельный VHDX успешно создан и удалён.

Docker Engine 29.9.2 / Compose 5.6.1: 2026-10-26 контейнерный core-check полностью
