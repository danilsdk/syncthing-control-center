2026-10-25, A / playerboom. Изменение поручено пользователем после A1.2–A1.4.
Заменяет предположение об уникальности startTime в draft-контракте. Review B0
ещё не выполнен; публикация и merge не входят в эту работу.

## Решение для MVP

`source_session_id` обозначает **эпоху подтверждённой непрерывности потока**,
а не гарантированно уникальный запуск процесса ОС. Это сохраняет существующий
ключ `(node_id, source_session_id, source_event_id)` и позволяет безопасно
отделить историю при недостатке доказательств.

В БД сохраняется ориентир потока — `StreamAnchor`:

- `id`: положительная позиция именно фиксированного `/rest/events`.
- `time_raw`: точная исходная строка времени события, включая доли секунды.
- `fingerprint`: SHA-256 безопасного нормализованного SourceEvent.

При чтении адаптер получает status → доступное окно events → status. Identity
и startTime должны совпасть между этими чтениями. Сохранённая эпоха продолжается
только при совпадении raw startTime и всего ориентира с событием текущего окна.
После успеха новым ориентиром становится последний элемент окна. Это не
продвигает курсор сохранённой истории само по себе.

Если ориентир отсутствует, не совпадает или uptime уменьшился, выбирается
новая эпоха. Старый курсор не применяется к ней: адаптер требует успешное
чтение с `since=0`. При смене эпохи между проверками long poll весь пакет
отвергается. Нет fallback на один startTime, на величину последнего id или
на предполагаемое отсутствие рестарта.

Сохранённый ориентир позволяет новому процессу backend продолжить ту же эпоху,
даже если самое первое событие уже вытеснено из буфера. Если сохранённое
событие тоже утрачено, непрерывность не доказывается: новая эпоха и явный
маркер потери непрерывности предпочтительнее молчаливого смешивания истории.
Сам backend-restart при наличии доказательства не меняет эпоху.

## Почему выбран этот вариант

| Вариант | Результат |
|---|---|
| Только startTime | Обрезается до секунды; уже выявленная коллизия |
| process_start_time_seconds | На Windows Prometheus тоже обрезает время до целых секунд; проверено кодом и двумя реальными процессами |
| CSRF/session cookie | Токены сохраняются в misc DB между запусками, имеют собственные сроки жизни; признаком запуска не являются |
| Только Starting.time | Точное время полезно, но событие может исчезнуть из конечного буфера |
| Отдельный агент с boot UUID | Требует нового сервиса и управления его жизненным циклом на каждом узле |
| Сохранённый ориентир и эпохи | Только существующий API и одна дополнительная JSONB-колонка; утрата доказательства явно видна |

Основания: [status v2.1.7](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/api/api.go),
[точное время и буфер событий](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/events/events.go),
[Windows collector v1.25.0](https://github.com/prometheus/client_golang/blob/v1.25.0/prometheus/process_collector_windows.go),
[постоянное хранение токенов](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/api/tokenmanager.go).

## Формирование ID и общий контракт

Новый ID — SHA-256 UTF-8 канонического JSON-массива:

```text
["scc:source-epoch:v2", str(node_id), start_time_raw, previous_session_id_or_null, seed_anchor]
```

Канонизация: `json.dumps(sort_keys=True, separators=(",", ":"))`, стандартное
`ensure_ascii=True`. `seed_anchor` — первый доступный элемент окна при создании
эпохи. Предыдущий ID включён при потере непрерывности/смене source, поэтому
даже совпавший первый элемент не заставляет повторно использовать старый ID.
Для продолжающейся эпохи ID не пересчитывается при сдвиге ориентира.

Fingerprint — SHA-256 такого же канонического JSON от
`SourceEvent.model_dump(mode="json")`. Произвольный upstream data, физические
пути и тексты ошибок сначала отбрасываются адаптером. globalID остаётся
диагностическим полем в отпечатке; курсором остаётся исключительно id.
Все исходные отметки времени сохраняются строками без datetime round-trip.

В `app.contracts.interfaces` добавлены StreamAnchor и SourceCheckpoint.
SystemObservation возвращает stream_anchor. EventBatch возвращает
source_checkpoint с UUID узла, raw startTime, ID эпохи и ориентиром; его ID
должен совпадать с верхним source_session_id. Нет пустого успешного доказательства.
SourceCheckpoint.anchor=None допускается только как legacy-состояние без
доказательства и не разрешает продолжить прежнюю эпоху.

Factory resolver возвращает `ResolvedNode(..., checkpoint=...)` из серверной БД.
Checkpoint другого UUID отвергается. Отсутствующее доказательство нельзя
подменить вычисленным только из startTime hash. Первый запрос событий без
сохранённого доказательства также начинается с нуля.

## Потребители A2/A3/B2

В managed_nodes добавлено nullable `source_stream_anchor` JSONB. Оно содержит
только id/time_raw/fingerprint, связано CHECK с заполненной сессией и не
заменяет last_event_id. A2 при регистрации может сохранить первое системное
наблюдение; при обычных запросах зарегистрированного узла не перезаписывает
курсор и каноническую историю. Resolver восстанавливает SourceCheckpoint из
UUID, source_start_time_raw, source_session_id и source_stream_anchor.

A3 — единственный писатель канонической истории MVP. Под блокировкой строки
узла он сверяет актуальный checkpoint и атомарно сохраняет:

1. Маркер границы, если эпоха изменилась.
2. Принятые события и обычные ограниченные HistoryGap внутри эпохи.
3. Новый source_session_id, raw startTime, source_stream_anchor из EventBatch
   и последний реально принятый id. Пустой пакет не двигает курсор.

Если checkpoint в БД уже изменён другим исполнением, старое наблюдение не
перезаписывает новое: пакет перечитывается. При session_changed коллектор
проверяет source и повторяет с нуля; ответ со старым курсором не принимается.
Утраченное содержимое не восстанавливается предположениями. При переходе
эпохи возможная неопределённость/перекрытие старого окна отмечается границей;
дедупликация гарантируется внутри эпохи, а не между недоказанно связанными окнами.

Два разных локальных маркера используют существующую категорию `kind=restart`:

- `SourceRestarted`: raw startTime изменился при том же Device ID.
- `SourceContinuityLost`: raw startTime тот же, но ориентир не подтвердился;
  это не утверждение о доказанном перезапуске ОС/Syncthing.

Оба имеют source_event_id=null и previous_session_id в безопасном payload.
Неизвестный диапазон между эпохами не оформляется вымышленным bounded HistoryGap.
UI и отчёт должны различать маркеры по event_type. Публичная форма Event прежняя.
B2 сравнивает ID эпохи до/после команды; новый ID или недостаточное доказательство
дают unknown, а не applied. HTTP и PostgreSQL общей транзакции не имеют.

## Миграция и обратимость

`a101_stream_anchor` следует за неизменённой a003_initial_schema. Сохраняет все
существующие строки, их source_session_id и курсоры. Legacy-строки получают
NULL-ориентир; при первом обращении через новый адаптер они не считаются
подтверждённой непрерывностью. A3 оформляет новую эпоху с маркером.
Маркер SourceContinuityLost разрешён DTO и CHECK БД.

Downgrade на пустом/legacy-состоянии проверен. Если уже есть новые ориентиры
или SourceContinuityLost, downgrade отказывается удалять доказательства или
переименовывать неопределённую границу в доказанный рестарт; требуется отдельный
план восстановления. Неудачный downgrade атомарно сохраняет схему и историю.
На рабочих базах миграция в этой задаче не запускалась.

```text
python -m pytest -c backend/pyproject.toml tests/unit tests/contract -q

python tests/integration/syncthing_adapter/check_d01.py
```

Первые две команды разделяют обычные тесты и собственный временный PostgreSQL.
Третья повторяет A1 pause/resume, восстанавливает клиента в новом процессе Python
из сериализованного checkpoint и проверяет конфликт coarse-time на настоящих
событиях после настоящего рестарта Syncthing. В тестовом транспорте startTime
и uptime намеренно фиксируются одинаковыми до/после; настоящий restart в одну
секунду этим не заявляется. В журнале отражаются фактические результаты и очистка.
