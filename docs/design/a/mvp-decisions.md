## D-01. События, курсор и перезапуск источника

- В MVP используется один фиксированный поток `/rest/events` каждого узла.
  Его фильтр не меняется во время работы; `id` и `globalID` не смешиваются.
- Сессия источника определяется по `startTime` из `/rest/system/status`.
  `source_session_id` — SHA-256 от UTF-8 строки `node_id + "\n" + startTime`.
  Исходную строку `startTime` сохранять без потери точности долей секунды.
- Уникальный ключ события: `(node_id, source_session_id, source_event_id)`.
  Прежняя пара `(node_id, source_event_id)` из плана заменяется этим ключом.
- Для узла сохраняются текущая сессия и последний принятый `id`. Запись пакета
  событий и продвижение курсора выполняются одной транзакцией. Повтор пакета
  не создаёт дубликаты. Перезапуск backend сам по себе не меняет сессию источника.
- При смене `startTime` курсор сбрасывается; фиксируется новая сессия,
  запрашиваются доступные события и свежий снимок состояния.
- Проверять сессию до и после получения пакета. Если источник перезапустился
  между запросами, пакет не привязывать к прежней сессии, а повторить чтение
  после определения новой сессии.
- Разрыв последовательности внутри сессии означает неполную историю.
  После разрыва выполняется сверка состояния; содержание потерянных событий
  не восстанавливается предположениями.

Владелец: A0 — поля и ограничения; A1 — доступ к API; A3 — сбор и восстановление.
Проверка: повтор пакета, разрыв, перезапуск backend, перезапуск Syncthing с
повторным номером события и перезапуск источника между запросами.

## D-02. Отключение, удаление правила и ручное возобновление

- Отключение или удаление правила прекращает автоматическое управление.
  Само действие не отправляет `paused=false` и не восстанавливает прежние настройки.
- После подтверждения отключения исполнитель не начинает новые команды по
  отключённой версии. Проверку версии и начало отправки сериализовать с
  изменением правила. Уже отправленную команду нельзя объявлять отменённой:
  её фактический результат сохраняется отдельно.
- UI показывает последнее наблюдаемое состояние и его время. Для актуальной
  паузы: «Расписание отключено. Папка остаётся на паузе». При устаревших данных
  указывается, что текущее состояние неизвестно.
- Для папки без активного правила доступна отдельная команда «Возобновить».
  Она требует авторизации, проходит через тот же адаптер и механизм подтверждения,
  попадает в историю с `source=manual` и пустым `rule_id`.
- При активном правиле ручное возобновление отвергается с конфликтом; UI
  предлагает сначала отключить расписание. Отдельного режима override в MVP нет.
- Удаление правила не удаляет историю. Попытка хранит снимок параметров и версии
  правила; её необязательная ссылка на удалённое правило становится пустой.

Владелец: B0/B1 — семантика и CRUD; B2 — ручная команда и исполнитель;
B3 — интерфейс; A0 — общий контракт и история без каскадного удаления;
A2 — общая защита API. Роутер ручной команды относится к зоне B2 (`executions.py`).
Проверка: отключение и удаление при паузе, конфликт ручной команды с правилом,
изменение версии до отправки и отключение при уже отправленной команде.

## D-03. Недельное расписание

- У папки допускается не больше одного активного правила. Ограничение
  обеспечивается и API, и частичным уникальным индексом PostgreSQL для `enabled=true`.
- Правило содержит непустой набор дней ISO: 1 — понедельник, 7 — воскресенье,
  один интервал с точностью до минуты и IANA timezone. Значение по умолчанию —
  `Europe/Moscow`; неизвестная зона, дубли/неверные дни и равные границы отвергаются.
- Начало включается, конец исключается: `[start_time, end_time)`.
  Внутри окна `desired_paused=false`, вне окна — `true`.
  При отсутствии активного правила желаемое состояние отсутствует, команды не создаются.
- Если конец раньше начала, окно переходит через полночь; выбранный день —
  день его начала. Например, пятница `23:00–02:00` заканчивается в субботу 02:00.
  Переход с воскресенья на понедельник обрабатывается тем же способом.
- Расчёт получает явный текущий момент UTC и переводит его в зону правила.
  Проверяется принадлежность локального дня и времени текущему либо начавшемуся
  накануне окну. Очередь отдельных заданий «на местное время» не создаётся.
- При DST отсутствующий местный час не догоняется. Оба вхождения повторившегося
  местного времени оцениваются одинаково; UTC-история различает эти моменты.
  Правило задаёт местные часы, а не гарантированную длительность в секундах.

Владелец: B0/B1 — примеры, расчёт и валидация; A0 — DTO и индекс БД;
B3 — форма. Проверка: обе границы, полночь, смена недели, DST, равные границы,
неверная зона и конкурентное включение второго правила.

## D-04. Попытка команды и подтверждение

- Для MVP работает один исполнитель. Перед отправкой и каждой повторной
  попыткой вычисляется актуальное состояние; старые команды не проигрываются.
- Попытка хранит узел, запись папки, источник `rule/manual`, снимок версии
  и параметров правила, `desired_paused`, время создания, отправки, проверки,
  завершения и код ошибки. Секреты в историю не включаются.
- Статусы: `pending` — ожидается результат; `applied` — подтверждено;
  `failed` — получен определённый отказ или подтверждено неприменение;
  `unknown` — результат установить нельзя; `cancelled` — отменено до отправки.
  `unknown` завершает эту попытку и учитывается отдельно от успехов/отказов.
- После PATCH выполняется новое чтение конфигурации этой папки и
  `/rest/config/restart-required`. Старый snapshot не подтверждает новую команду.
- `applied` означает: после операции прочитано нужное `paused`, перезапуск
  не требуется, версия правила остаётся актуальной. Это подтверждение
  конфигурации; фактическую передачу файлов доказывают отдельные интеграционные тесты.
- Если после отправки правило изменилось, сохранить наблюдаемый результат,
  но не выдавать его за подтверждение новой версии. При неактуальной версии
  результат исполнения старого правила помечается `unknown` с причиной
  `rule_changed_after_send`; следующая сверка рассчитывает текущее правило.
- Таймаут с неопределённым результатом, ошибка чтения или требуемый перезапуск
  дают `unknown` с отдельным кодом причины. Перезапуск автоматически не выполняется.
- Если значение уже совпадает до отправки, сохраняется наблюдение, а новая
  успешная попытка команды не создаётся. Это исключает завышение числа успехов.

Владелец: A0 — модель/интерфейс; A1 — адаптер; B2 — логика; A4 — запуск одного worker.
Проверка: HTTP 200 без изменения, таймаут после отправки, требуемый перезапуск,
смена правила до/после отправки, восстановление узла и отсутствие лишних команд.

## D-05. Наблюдения и две обязательные метрики

- Сохранять каждую выполненную проверку API узла, включая неуспешные:
  время, результат и безопасный код причины. Ошибка ключа, недоступность сети
  и некорректный ответ остаются разными причинами.
- Проверки узла отличаются от снимков его папок. Для метрики доступности
  используется одна запись на одну проверку узла; число папок не влияет на знаменатель.
  A0 предусматривает это в `status_snapshots` без обязательного нового сервиса хранения.
- Метрика 1: `applied / (applied + failed)` среди попыток, завершённых за период.
  Автоматические и ручные команды можно фильтровать по `source`.
  `pending`, `unknown`, `cancelled` показываются отдельными числами.
- Метрика 2: успешные проверки API / все выполненные проверки API за период,
  отобранные по времени наблюдения. Название: «Доля успешных проверок API».
  Это не фактический uptime устройства.
- Отсутствие выполненных проверок означает пробел мониторинга; оно не добавляет
  ни успех, ни отказ. Для графика показываются разрывы наблюдений и число проверок.
- Нулевой знаменатель любой метрики даёт `null` и подпись «Нет данных», а не 0%/100%.
- Все отметки истории — UTC. Число ошибок по дням допустимо добавить как
  дополнительную таблицу после двух обязательных показателей.

Владелец: B0 — формулы; A0/A3 — схема и записи; B4 — расчёт и экран.
Проверка: ручной расчёт на небольшом наборе с ошибками доступа, неизвестными
попытками, отменами, несколькими папками узла и периодом без наблюдений.
