## Цикл и владение ресурсами

Один последовательный проход enabled-узлов по внутренним UUID, без параллельных
сборщиков в MVP. Интервал наблюдения — Settings.observation_interval_seconds
(30 секунд); Clock внедряется. read_events использует timeout_seconds=0, чтобы
не удерживать длинный poll первого узла перед проверкой второго. HTTP-таймауты
адаптера не являются общим SLA цикла; пропущенные тики не догоняются фиктивными
проверками. Расписание вызовов и singleton процесса подключает A4.

1. Прочитать доверенные metadata и канонический checkpoint узла, закрыть SQL.
2. Взять отдельную принадлежащую этой попытке фабрику A1 с NodeResolver A2,
   прочитать пакет событий. На session_changed допускается одна явная попытка
   установить текущий source и прочитать since=0; иных немедленных повторов нет.
3. Подготовить и атомарно записать пакет по правилам ниже. При конфликте снимка
   не применять его; новое чтение — в следующем цикле. Закрыть фабрику в finally.
4. Независимо от успеха event poll выполнить одну явную проверку read_system,
   затем доступные config/runtime проверки. После успешной записи boundary/gap
   эта фаза является сверкой текущего состояния. После падения между фазами
   следующий старт всё равно выполняет новую проверку состояния.
5. Записать фактически полученные наблюдения отдельной транзакцией; закрыть ресурсы.

Фабрики попыток не разделяются с API/B2. HttpSyncthingAdapter обновляет внутренний
checkpoint при чтениях до DB commit. Поэтому после rollback, неизвестного исхода
commit или конфликтующего CAS клиент не переиспользуется; новый resolver читает
только каноническую БД. Публичный интерфейс A1 расширять для очистки private cache
не нужно. В тестах внедряется владелец фабрики с проверяемым close.

Сеть не удерживает SQL-соединения/row locks. Перед применением под FOR UPDATE
сверяются enabled, connection_ref, закреплённый Device ID, разрешённый серверный
target и полный предыдущий checkpoint/cursor. Сравнения только updated_at
недостаточно как контракта: обычное чтение A2 также обновляет metadata.
Наблюдения, реально выполненные до конкурентного disable, могут остаться в истории,
но не меняют выключенный узел/его canonical checkpoint. Невыполненных проверок нет.

## Атомарное сохранение событий — A3.2

Источник — исключительно EventBatch от A1. Проверяются UUID checkpoint, совпадение
эпохи, непустой anchor, возрастающие положительные bigint ID и пригодные поля
публичного Event/SQL. Курсор — SourceEvent.id, не global_id и не anchor.id.
Некорректный элемент отвергает весь пакет, а не молча пропускается с продвижением.
SourceEvent.type длиннее SQL String(80) не обрезается: это invalid_response.

| Случай | Запись |
|---|---|
| Та же эпоха, позиции идут подряд | Source-события; cursor = последний принятый id |
| Повтор уже записанной позиции | ON CONFLICT для частичного ключа node/session/id; существующая строка не переписывается |
| Внутри подтверждённой эпохи отсутствуют позиции | HistoryGap с включительным [from_id,to_id], затем source-события; одна транзакция |
| Новый raw startTime при том же Device ID | SourceRestarted, previous_session_id и доступные события новой эпохи |
| Raw startTime прежний, доказательство не подтвердилось | SourceContinuityLost; это не утверждение о доказанном рестарте процесса |
| Пустой пакет той же эпохи | Курсор прежний; допускается обновить доказательство той же эпохи |
| Пустой пакет другой эпохи | Переход откладывается до пригодного непустого чтения с нуля; старый курсор не переносится в новую эпоху |
| Ошибка или конкурентная запись checkpoint | Никаких частичных событий/маркеров/продвижения; новое чтение из канонической БД |

Для прежней эпохи expected начинается с last_event_id+1, в том числе с 1 при
cursor=0. При переходе эпохи первый доступный ID задаёт новую нижнюю границу;
bounded gap через старую/новую эпоху не выдумывается. Промежутки между принятыми
событиями новой эпохи уже имеют известные границы. Маркер перехода сообщает о
неопределённости и возможном перекрытии старого окна. Дедупликация гарантируется
внутри эпохи; недоказанное перекрытие между эпохами не склеивается молча.

Одна транзакция сохраняет boundary/gaps/source rows и поля managed_nodes:
source_start_time_raw, source_session_id, source_stream_anchor, last_event_id.
Локальные маркеры имеют source_event_id=null и не продвигают курсор сами по себе.
Повтор маркера предотвращается сверкой прежнего checkpoint под блокировкой:
после успешного commit исходный снимок уже устарел. Падение до commit откатывает всё.

Папка сопоставляется только по (node_id, syncthing_folder_id), включая известную
present=false папку. Если соответствия ещё нет, source event сохраняется с
folder_id=null; из произвольного event data новая папка не создаётся. Актуальный
полный config-список создаёт/возвращает mapping отдельно. Чужой UUID не используется.

Persisted payload строится заново по EventPayload allowlist: from_id/to_id/state/
previous_session_id. Сырые source data, пути, имена файлов, ключи, тела ответов
и исключения не сохраняются. occurred_at — разобранное UTC время события;
received_at — Clock коллектора. Точные raw timestamps остаются в anchor согласно D-01.

## Наблюдения и метрики — A3.3

Один логический node probe — явный read_system с ожидаемым Device ID. Он создаёт
ровно один StatusSnapshot(scope=node), независимо от количества папок, внутренних
status-запросов адаптера и результата read_events. Именно эти сохранённые проверки
коллектора образуют набор мониторинга для B4; фоновые transport-вызовы A1 и чтения
реестра A2 не превращаются задним числом в дополнительные пробы.

Успешный system + ошибка event poll не означают неуспешный node probe. Poll-ошибка
возвращается безопасным кодом результата цикла/журнала; cursor прежний. Она сама
по себе ещё не доказывает bounded gap. Отказ явного system даёт один failed node
snapshot с кодом адаптера, без чтений папок и выдуманных failed folder rows.

Config и runtime — два различных наблюдения папки, существующий Snapshot DTO
допускает их без смены схемы:

- Успешный полный config-список: по одной folder-записи на полученную конфигурацию,
  actual_paused заполнен, runtime/counters=null, observed_at=config.observed_at.
- Попытка runtime: отдельная folder-запись с runtime/counters и его временем;
  actual_paused=null. При отказе success=false, все измерения null, безопасный
  error_code с префиксом runtime_ и кодом адаптера. Старый runtime не копируется.
- Ошибка полного config-списка: ни present=false, ни несуществующие измерения
  папок не создаются; результат config-фазы явно возвращается/журналируется.
  Неисполненный runtime после такого отказа не считается проверкой.

Так runtime paused-папки с непредставимым state не стирает успешный config=true
и не выглядит успешным runtime. Две folder-записи не увеличивают знаменатель
доступности: B4 использует только scope=node. Отсутствие выполненного цикла —
пробел мониторинга, а не 0%, 100% или искусственная ошибка.

Наблюдения сохраняются отдельно от транзакции event batch: ошибка парсинга
событий/CAS не должна удалять фактически выполненный node probe. При недоступной
БД нет гарантии долговечной очереди в памяти; потерянные пробы не восстанавливаются
фиктивными строками. После восстановления выполняется новая проверка.

Кеш Node/Folder обновляется только свежими пригодными наблюдениями с повторной
проверкой enabled/identity/target под блокировкой. Времена не регрессируют.
Полный успешный список меняет present; ошибка сохраняет прежние значения/времена.
Чтения статуса не записывают canonical checkpoint; это делает только event-фаза.
История и правила при исчезновении папки не удаляются. Расписания не вычисляются,
команды paused не отправляются, B2 лишь получает актуальные наблюдения.

## API истории — A3.4

Оба маршрута размещаются в api/events.py и подключаются через общую require_admin.
Это чтения только БД, без сетевого опроса; старые/disabled узлы доступны в истории.

| Маршрут | operationId | Ответы | Фильтры |
|---|---|---|---|
| GET /api/events | list_events | 200 EventPage, 401/422/503 Error | node_id, folder_id, from, to, limit, offset |
| GET /api/snapshots | list_snapshots | 200 SnapshotPage, 401/422/503 Error | те же + scope=node/folder |

limit=50, 1–100; offset>=0. From/to — существующие wire aliases с UTC Z;
интервал [from,to), при заданных обеих границах from<to, иначе 422 invalid_period.
Отбор events по received_at, snapshots по observed_at; сортировка соответствующее
время DESC, id DESC. Total считается после всех фильтров. Node/folder фильтры —
AND; отсутствие совпадений возвращает пустую страницу, новые 404 не вводятся.
Scope=node вместе с folder_id также даёт пустую страницу. Одного фильтра без
второго достаточно; ограничение периода аналитики сюда не переносится.
Error/request_id/no-store и adminSession унаследованы от A2. Новых DTO нет.

## Использование результата A3.2

Реализованы collection/planning.py (чистый план пакета), store.py (SQL) и
service.py (одна ограниченная попытка с принадлежащей ей фабрикой A1/A2).
EventCollector/ EventStore/ CollectionResult экспортированы из app.collection.
Обычный вызов из будущего worker или проверочного драйвера:

```python
from uuid import UUID
from app.collection import EventCollector
from app.config import Settings
from app.contracts.interfaces import SystemClock
from app.db import Database

settings = Settings()
database = Database(settings)
try:
    collector = EventCollector(settings, database, SystemClock())
    result = collector.collect(UUID("00000000-0000-0000-0000-000000000001"))
finally:
    database.close()
```

Нужен UUID уже зарегистрированного узла, мигрированная PostgreSQL и серверные
connections; пример UUID — публичный placeholder. Вызов не запускает scheduler,
не создаёт snapshot и не меняет paused/правила/кеш состояния. Clock/фабрика
внедряются в проверках, SQL-соединения не удерживаются во время сетевых операций.

CollectionResult содержит node_id, outcome, events_inserted, markers_inserted,
cursor, reconcile и безопасный error_code:

- stored — транзакция подтверждена; reconcile=true при boundary/gap, который
  должен вызвать фазу наблюдений A3.3.
- conflict — исходные identity/alias/target/checkpoint/cursor уже изменились;
  пакет не применён. Изменение только display_name/api_status не является CAS
  канонической истории.
- deferred — новая эпоха без событий; прежний checkpoint/cursor сохранён.
- skipped — узла нет или он disabled; фабрика не создавалась.
- error — фиксированный код адаптера, database_unavailable, internal_error или
  resource_close_failed. Для database_unavailable commit мог фактически пройти;
  следующий вызов перечитывает БД и не создаёт дубль. При ошибке закрытия после
  подтверждённого commit результат сохраняет реальные счётчики/cursor.

Source event names принимаются только как ASCII-имена [A-Za-z][A-Za-z0-9_]{0,79};
пути, control chars и слишком длинные типы отвергают пакет. В source payload
остаётся только безопасный state для StateChanged. Поля bounded gap и предыдущей
эпохи создаёт сам планировщик локальных маркеров, источник не может их подделать.
Неизвестный внешний Folder ID не сохраняется как путь и не создаёт mapping:
event остаётся с folder_id=null; известный present=false mapping сохраняется.

Повтор проверки из backend-окружения (PowerShell):

```powershell
$env:PYTHONPATH = (Resolve-Path backend).Path
python -m pytest -c backend/pyproject.toml tests/unit tests/contract tests/integration/auth tests/integration/registry tests/integration/collection -m "not postgres" -q -W error
python tests/integration/collection/check_postgres.py --bin-dir "C:\Program Files\PostgreSQL\18\bin"
```

Отдельный runner создаёт только собственный кластер scc-a32-pg-* на loopback
со случайным портом/паролем и SCRAM; мигрирует, выполняет тесты и удаляет его.
Рабочий DB URL не принимается, fixtures требуют точный private marker/name/user.
Есть опциональный --junitxml для внешнего файла результата. Fixtures используют
подставной Syncthing; это доказательство SQL/логики, не реальной A3.5-интеграции.

## Итог A3.5 и передача

2026-10-26, 02:42–02:44 MSK: Python 3.12.14, PostgreSQL 18.6, два нативных
Syncthing v2.1.7. Настоящий HTTP API с login/scrypt/cookie/CSRF и SQL; каждый
collection pass запускался в новом процессе без подмены адаптера или времени.
9 сценариев прошли, сохранены 1146 событий, 46 snapshots, из них 10 node-проб;
дубли source positions отсутствуют. Числа зависят от активности реального стенда.

600 маленьких демонстрационных файлов действительно переданы между узлами.
Это переполнило стандартный буфер из 1000 событий; после регистрации с актуальным
anchor и cursor=0 сохранён HistoryGap [1,276], затем доступные события. Между
контрольным чтением окна и пакетом источника пришло ещё одно событие, поэтому
граница взята из реально принятого пакета. Повтор того же пакета отклонён CAS
без новых строк. Константа буфера — в [исходнике Syncthing v2.1.7](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/api/api.go).

Проверены outage одного узла при работающем втором, сохранность старого кеша/
UUID и доступность истории из БД, успешная новая проба после возврата, настоящая
смена startTime/эпохи после рестарта, восстановление anchor/cursor свежим процессом.
Утрата доказательства при прежнем startTime проверена явным legacy-состоянием
БД (anchor=NULL) с настоящим адаптером/источником. Это отдельное условие,
а не заявление о физическом переполнении именно после сохранённого anchor.
Config paused и неуспешный runtime остались разными снимками; папки не увеличили
node-знаменатель. Полный исходный config папок восстановлен, процессы остановлены,
созданные файлы удалены. Подробности: [воспроизведение](../../../tests/integration/collection/README.md),
[публичный результат](../../../tests/integration/collection/evidence/a35-native-2026-10-26.json).

Финальные наборы: 427 passed / 190 deselected без PG; 69 passed / 14 deselected
