# Начало A0: роли, задачи и оставшиеся решения

Дата проверки: 24 октября 2026 года. Текущий участник — **A / playerboom**;
второй разработчик — **B / danilsdk**. Подключение GitHub проверено под `playerboom`.
При смене сессии доступы и состояние PR проверяются заново.

## Что уже определено

- Предмет и границы — два экземпляра Syncthing, одна–две демонстрационные папки,
  один администратор, управление расписанием, история и две метрики.
- Пять продуктовых вопросов закрыты [решениями D-01–D-05](mvp-decisions.md).
  Общие типы/схема/блокировки реализованы в A0.1–A0.4; сервисы ещё предстоят.
- A владеет общей схемой БД, миграциями, интерфейсом адаптера и контрактом.
  B реализует свои модули с этими моделями; необходимые изменения схемы делает A.
- Существующее распределение на двух участников сохраняется. Подробные карточки
  A0–A5/B0–B5 подготовлены в [PR H0 №1](https://github.com/danilsdk/syncthing-control-center/pull/1).
  На дату проверки PR открыт и не объединён; карточки ещё не находятся в `main`.

## Задачи двух разработчиков

| Этап | A / playerboom | B / danilsdk | Проверяемый результат |
|---|---|---|---|
| Подготовка | A0: FastAPI, общие модели, миграция, DTO и контракт | B0: примеры времени, команд, метрик и план UI | Общий контракт позволяет реализовывать модули независимо |
| Основа | A1: адаптер и реальные ответы Syncthing | B1: расписания и API правил | Проверенный API источника и детерминированный расчёт правил |
| Управление | A2: узлы, папки, авторизация | B2: применение, ручное возобновление и история | Два узла доступны через защищённый API; результат команды проверяется |
| Наблюдение/UI | A3: события, снимки и восстановление | B3: вход, обзор, правила и история | Перезапуски не ломают курсор; основной сценарий доступен из UI |
| Интеграция | A4: Compose, CI и системные проверки | B4: аналитика и пользовательский E2E | Реальный стенд, две метрики и полный пользовательский сценарий |
| Защита | A5: интеграционная часть и сборка отчёта | B5: автоматизация, интерфейс и демонстрация | Проверенный обоими отчёт с отдельным вкладом участников |

Каждый разработчик пишет тесты своей логики и собственную часть отчёта.
PR проверяет второй участник. Наличие задач в документах не означает их завершение
или создание GitHub Issues: на дату проверки в GitHub обнаружен только PR H0.

## Что требуется перед работой с harness

1. Провести отдельный содержательный review H0, затем включить принятые правила
   в `main`. Настоящее поручение фиксирует продуктовые решения; публикация этого
   документа сама по себе не означает approval или merge H0.
2. Обновить локальные рабочие копии и проверить, что текущая учётная запись — A,
   а B работает под своим аккаунтом. Использовать отдельную ветку A0.
3. Для Windows проверить Git, Python и Docker Desktop. На этой машине Git и
   доступ к GitHub подтверждены; Python доступен через bundled runtime Codex.
   Docker и применение миграции к PostgreSQL в рамках фиксации решений не проверялись.

Проектирование A0 можно начинать до слияния H0. Команды `start/validate` из H0
и штатный цикл приёмки используют уже принятый harness. Непроведённый review
не подменяется зелёным CI или текстом инструкции из PR.

## Что решается внутри A0, а не блокирует его начало

| Вопрос | Решение для старта и результат A0 |
|---|---|
| Версии и зависимости | Python 3.12 соответствует подготовленному CI H0. FastAPI, SQLAlchemy 2, Alembic, PostgreSQL; конкретные совместимые версии и способ воспроизводимой установки фиксирует A0 |
| БД | Одна PostgreSQL; A0 создаёт миграцию и проверяет её на пустой тестовой БД. SQLite не заменяет проверку PostgreSQL-ограничений |
| Общие типы | A0 фиксирует внутренние ID, отдельные Syncthing ID, UTC/ISO 8601, DTO, формат ошибок и пагинацию; включает поля D-01–D-05 |
| Авторизация | A0 определяет общую зависимость авторизации и контракт входа. Реальную защиту реализует A2; заглушка до A2 запрещает управление по умолчанию |
| Адаптер | A0 описывает интерфейс и ошибки; A1 проверяет его на зафиксированной версии Syncthing. B2 использует fake того же интерфейса |
| Worker | Один отдельный процесс с периодической сверкой. В A0 определить точку запуска и конфигурацию; API-процессы не запускают собственные копии |
| Frontend | Стек выбирает B в B0. Он не блокирует модели, миграцию и интерфейсы A0 |
| VPS и секреты | Адрес VPS, домен и действующие ключи не нужны для A0. A0 использует тестовую БД и шаблоны без реальных секретов |

Выбор библиотек и названий полей — обычная работа A0. Дополнительных решений
пользователя о продукте перед началом A0 не требуется. Перед принятием общего
контракта нужен review B0: примеры времени, версии команд и формулы метрик
должны согласоваться с D-01–D-05.

## Ранний стенд и зависимости

Сначала A0 и B0, затем A1 и B1. Первые unit-проверки B2 используют fake;
UI B3 может готовиться на согласованных JSON-примерах.

Ранний стенд относится к A1: его существующая область `deploy/syncthing/`
позволяет поднять два изолированных источника для проверки адаптера.
Поэтому ранние реальные проверки не должны ждать B3. A4 сохраняет зависимость
от готовых компонентов для окончательной сборки всего приложения.
Это уточняет прежнее предложение выделить раннюю часть A4: отдельная новая
карточка не требуется, ранняя работа уже помещается в A1.

## Критерии окончания A0

Подэтапы A0.1–A0.4 описаны в [плане передачи](a01-review.md) и реализованы.
Подготовленный [контракт](../../contracts.md) имеет статус draft до review B0.
Пользователь выбрал единое review после готовности всего A0.1–A0.4;
промежуточные результаты накоплены в PR №2; реализация подготовлена к review.

- Минимальное приложение запускается; настройки разделены с секретами.
- Базовая миграция применяется к пустой PostgreSQL.
- Модели включают сессию событий, сохранённый курсор, версии правил,
  историю без каскадной потери и результаты неуспешных проверок.
- Ограничение одного активного правила проверяется на PostgreSQL.
- DTO, адаптер, ошибки, авторизация и запуск worker описаны в общем контракте.
- B проверил контракт на примерах D-01–D-05; значимые разногласия закрыты.
- Выполнены применимые проверки A0 и сохранены их настоящие результаты.
  Подготовка реализации к review не заменяет приёмку общего контракта B.
