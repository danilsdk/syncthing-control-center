## Результат A1

Нужен синхронный адаптер одного управляемого экземпляра Syncthing с фабрикой
по внутреннему UUID узла, ограниченными таймаутами и безопасными ошибками.
Его потребители — реестр A2, коллектор A3 и исполнитель B2.
Протоколы и внутренние DTO уже подготовлены в
[interfaces.py](../../../backend/app/contracts/interfaces.py);
правила использования — в [передаче A0.4](a04-handoff.md).

Наблюдения и отправка команды — отдельные операции. `set_paused` не назначает
статус Execution и не подтверждает применение. В A1 проверяется возможность
наблюдать результат на стенде; окончательный алгоритм подтверждения, актуальность
правила, блокировки и история команд принадлежат B2.

## Решения для MVP

### Версия и изолированный стенд

Для проверки выбирается **Syncthing v2.1.7**, опубликованный 2026-10-21 как
[стабильный официальный релиз](https://github.com/syncthing/syncthing/releases/tag/v2.1.7).
Использовать конкретный архив и проверить его SHA-256 до запуска:

- `syncthing-windows-amd64-v2.1.7.zip`:
  `3ce7da770f546a8d02b65b2e7ee31f2a3b8b7c3f990ede045590cca4172ecfe1`.
- Для будущего Linux-стенда `syncthing-linux-amd64-v2.1.7.tar.gz`:
  `2edc416e7ed136b7c858ed5f3f02a3b8316589605e54c380228ceea7acbf0142`.

Это фиксация версии и метаданных релиза, а не доказательство совместимости:
загрузка архива, проверка хеша и реальные ответы относятся к A1.1.
Если релиз не удовлетворит проверкам, причину и новую точную версию зафиксировать
до реализации зависимых сценариев.

Docker CLI и Docker Desktop в стандартном расположении на этой машине
не обнаружены. Первый стенд A1 — два переносимых процесса Windows из одного
проверенного архива. У каждого собственные home/config/data, API-ключ,
Device ID и порты; настройки существующих экземпляров не используются.
Официальная [CLI-документация](https://docs.syncthing.net/users/syncthing.html)
описывает отдельный home и GUI address.

План стенда:

- API слушает только loopback; стартовые кандидаты портов — 18384 и 28384.
  Перед запуском проверить свободные порты, не останавливая чужие процессы.
- Два экземпляра соединяются по явно заданным локальным адресам. Глобальное
  обнаружение, relay, NAT и автоматическое обновление в стенде отключены.
- Одна общая тестовая папка и вторая контрольная папка с нестандартными
  параметрами. Личные папки и работающие базы Syncthing не используются.
- Секреты генерируются для стенда; runtime, архивы и ключи остаются в
  игнорируемой локальной папке. В Git — сценарии, шаблоны и обезличенные fixtures.
- Запуск/остановка управляют только процессами этого стенда. Готовность и
  синхронизация проверяются наблюдениями с конечным сроком ожидания.
- Запускать фоновые помощники без отдельных видимых окон. Браузер открывать
  только для необходимой ручной проверки.

Окончательный Compose всего приложения остаётся в A4. Для A1 достаточно
воспроизводимого изолированного стенда и переносимых сценариев API-проверок.

### Минимальный набор API

| Метод адаптера | API Syncthing | Что получить/проверить |
|---|---|---|
| `read_system()` | `GET /rest/system/status` | myID, исходный startTime, время наблюдения, сессия источника |
| Проверка версии стенда | `GET /rest/system/version` | Фактическая версия совпадает с выбранной |
| `list_folders()` | `GET /rest/config/folders` | ID, label и paused каждой папки |
| `read_folder(id)` | `GET /rest/config/folders/{id}` | Конфигурация именно указанной папки |
| `read_runtime(id)` | `GET /rest/db/status?folder=...` | state, needBytes, pullErrors; неизвестные значения не выдумываются |
| `set_paused(id, value)` | `PATCH /rest/config/folders/{id}` | Только JSON `{"paused": true/false}` |
| `restart_required()` | `GET /rest/config/restart-required` | Требуется ли рестарт для применения конфигурации |
| `read_events(since, timeout)` | `GET /rest/events` | Один фиксированный поток с возрастающими id |

Основания: [конфигурация](https://docs.syncthing.net/rest/config.html),
[состояние узла](https://docs.syncthing.net/rest/system-status-get.html),
[состояние папки](https://docs.syncthing.net/rest/db-status-get.html),
[события](https://docs.syncthing.net/rest/events-get.html).
Документация — ориентир; формы fixtures подтверждаются выбранным бинарником.
Запрос runtime папки использовать по необходимости, учитывая отмеченную
в документации стоимость этого запроса.

### Ошибки, секреты и время

- Доступ только по разрешённой серверной конфигурации `NodeConnection`;
  URL и ключ не поступают из браузера. Внешний Folder ID кодируется одним
  сегментом пути, query-параметры задаются отдельно.
- Проверять Device ID относительно ожидаемой идентичности зарегистрированного
  узла; первичное обнаружение и последующая проверка различаются явно.
  Способ передачи ожидаемого ID фиксируется внутри реализации фабрики,
  без молчаливого изменения общего протокола A0.
- Обычный HTTP timeout — 5 секунд. Для событий server timeout — 15 секунд,
  HTTP read timeout — 20 секунд. Любой параметр ожидания должен быть ограничен.
- Пустой список событий корректен. Неизвестный runtime state сохраняется строкой;
  отсутствующее наблюдение не превращается в idle, false или ноль.
- Применяется существующий AdapterError: timeout/unreachable/auth_error/
  not_found/invalid_response/identity_mismatch/session_changed.
- Для записи 401/403/404 могут означать доказанный not_applied. Таймаут,
  разрыв связи и 5xx дают unknown. Скрытых повторов PATCH нет.
- В логах и исключениях нет ключей, URL и сырых ответов. Чтение JSON ограничено
  по размеру; redirect не должен пересылать секреты другому адресу.
- Фабрика освобождает принадлежащие ей ресурсы через close. Транспорт
  синхронный. Выбор HTTP-библиотеки — часть A1.2; внешняя runtime-зависимость
  требует отдельно оформить изменение общих dependency-файлов, которые
  текущая карточка A1 не разрешает менять.

## Подэтапы

| Этап | Работа | Проверяемый результат |
|---|---|---|
| **A1.1 — стенд и API** | Проверить архив/версию; подготовить запуск двух экземпляров; выполнить чтения и получить обезличенные ответы | Оба API доступны, версия зафиксирована, реальные схемы и особенности записаны; секреты не включены |
| **A1.2 — чтение и фабрика** | Реализовать транспорт, factory, system/folders/runtime/restart-required, безопасные ошибки и закрытие ресурсов | Все методы чтения возвращают DTO A0; покрыты неверный ключ, timeout, недоступность, 404 и повреждённый JSON |
| **A1.3 — события и сессия** | Реализовать long polling, проверку сессии до/после запроса и безопасную нормализацию событий | Пустой пакет корректен; restart и смена идентичности обнаруживаются; id не смешан с globalID; наносекунды startTime сохранены |
| **A1.4 — управление паузой** | Реализовать PATCH только paused и проверить pause/resume на стенде | Наблюдение конфигурации и restart-required отделено от HTTP-ответа; соседние поля и папки не изменены; нет скрытого retry |
| **A1.5 — приёмка и передача** | Пройти весь набор contract/integration, воспроизводимый сценарий и подготовить передачу A2/A3/B2 | Зафиксированы команды, версия, fixtures, реальные результаты, ограничения и ручная проверка перед merge |

Тесты соответствующих методов добавляются в каждом подэтапе. A1.5 объединяет
готовые проверки и реальные доказательства. Общий API A0 и семантика B2
не переписываются внутри адаптера.

### События A1.3

Один фиксированный `/rest/events`, без произвольного изменения фильтра между
запросами. Курсор — id потока; globalID используется только для диагностики.
Сессия вычисляется существующим helper A0 из внутреннего UUID узла и исходного
startTime без нормализации точности. Статус источника читается до и после
long poll; пакет при смене сессии отклоняется целиком.
В EventPayload остаются только разрешённые общим контрактом поля.
Файловые пути и произвольный payload не сохраняются.
Курсор, дедупликация, разрывы истории и транзакции БД реализуются в A3;
A1 предоставляет данные и ошибки, необходимые этим сценариям.

### Пауза A1.4

Официальный [issue #10389](https://github.com/syncthing/syncthing/issues/10389)
описывает сброс rescanIntervalS и fsWatcherEnabled при PATCH paused в версии
2.0.8. Его применимость к 2.1.7 ещё не проверена. Поэтому до/после каждой
команды нужно сравнить остальные поля конфигурации целевой папки и контрольную
папку. Обход через перезапись всей конфигурации в MVP не используется.

На стенде пройти pause → наблюдение → resume → наблюдение и ограниченную
проверку передачи тестового файла. Для объекта «узел A — папка X» убедиться,
что конфигурация такой же папки X на узле B не была изменена.
HTTP-успех, конфигурационный paused, runtime, restart-required и сессия
сохраняются в отчёте как разные факты. Автоматического рестарта нет.

## Готовность и незавершённые части

Для приёмки нужны реализация всех методов протокола, contract-проверки успехов
и отказов, реальные чтения и смена паузы на двух изолированных экземплярах,
сохранность соседних настроек, доказательство поведения при restart и
неопределённом исходе записи. Человек просматривает реальное изменение
конфигурации перед merge согласно инструкциям адаптера.

На момент планирования ничего из этих реальных испытаний не выполнено.
Вопросов о продукте, требующих решения пользователя перед A1.1, не выявлено.
Проверка архива, готовность локальных портов, реальные формы API и выбор
HTTP-транспорта выполняются в указанных подэтапах. Принятие A0 и H0 остаётся
условием окончательной интеграции и приёмки зависимого результата.
