# Метрики и данные для аналитики B0

Статус: формулы для B4 и требования к сборщику A3. Все периоды полуоткрытые:
`[from, to)`, обе границы задаются UTC, максимум 31 сутки.

## Обязательные показатели

### Доля подтверждённых команд

Для попыток, завершённых в периоде по `completed_at`:

```text
command_success_ratio = applied / (applied + failed)
```

`unknown`, `pending` и `cancelled` возвращаются отдельными счётчиками и не
становятся ни успехом, ни отказом. Фильтр `source=rule|manual` может ограничить
выборку, но не меняет формулу. При нулевом знаменателе отношение равно `null` и
показывается как «Нет данных».

### Доля успешных проверок API

Для проверок узла, наблюдённых в периоде по `observed_at`:

```text
api_probe_success_ratio = successful_node_probes / all_completed_node_probes
```

В знаменатель входит одна запись `scope=node` на одну фактическую проверку,
включая `unreachable`, `auth_error` и `invalid_response`. Снимки папок и число
папок не влияют на знаменатель. Отсутствие записи — пробел мониторинга, а не
успешная проверка и не ошибка. При нулевом знаменателе возвращается `null`.

Это доля успешных наблюдений API, а не обещание uptime устройства или доступности
файлов.

## Что должен сохранять A3

- Для каждой проверки узла: `node_id`, UTC `observed_at`, `scope=node`,
  `success`, безопасный `error_code` и source session, если она известна.
- Для каждого снимка папки: `folder_id`, UTC `observed_at`, `success`,
  `actual_paused`, runtime state и безопасный код ошибки; не записывать секреты,
  физические пути и сырые ответы.
- Для каждой попытки B2: `status`, источник, `completed_at`, `created_at`,
  `verified_at`, `error_code`, `rule_version` и внутренние ID.
- Разрыв истории событий (`HistoryGap`) сохранять отдельным gap-маркером
  (`kind=gap`, `event_type=HistoryGap`), а не результатом проверки доступности.
  Если `system/status` успешно прочитан и разобран, node-snapshot остаётся
  успешным даже при таком разрыве; снимок папки определяется только своей
  фактической проверкой. Неуспешный snapshot создавать только для реально
  неуспешного соответствующего наблюдения; пропущенные значения не
  восстанавливать догадкой.

## Пример ручного расчёта

За период есть 3 попытки: `applied=1`, `failed=1`, `unknown=1`. Результат
`1/(1+1)=0.5`; неизвестная попытка отображается отдельно. Если есть 4 проверки
узла (`ok`, `ok`, `unreachable`, `auth_error`), результат `2/4=0.5`. Если
проверок нет, API возвращает `null`, а UI показывает «Нет данных».
