# Метрики и данные для аналитики B0

Все периоды полуоткрытые `[from, to)`. Обе границы обязательны и задаются в UTC
с суффиксом `Z`. Максимальная длина периода — 31 сутки.

## Обязательные показатели

### Доля подтверждённых команд

Для попыток, завершённых в периоде по `completed_at`:

```text
command_success_ratio = applied / (applied + failed)
```

`unknown` и `cancelled` считаются отдельно по `completed_at`.
`pending_created` считает попытки, которые ещё ожидают подтверждения и были
созданы в периоде. Эти три счётчика не входят в знаменатель. Фильтр
`source=rule|manual` применяется ко всем счётчикам команд. При нулевом
знаменателе отношение равно `null` и показывается как «Нет данных».

### Доля успешных проверок API

Для проверок узла, наблюдённых в периоде по `observed_at`:

```text
api_probe_success_ratio = successful_node_probes / all_completed_node_probes
```

В знаменатель входит одна запись `scope=node` на одну фактическую проверку,
включая `unreachable`, `auth_error` и `invalid_response`. Снимки папок и число
папок не влияют на знаменатель. Отсутствие записи — пробел мониторинга, а не
успешная проверка и не ошибка. При нулевом знаменателе возвращается `null`.

Показатель описывает результаты выполненных наблюдений API.
Фильтр `source` оставляет выборку проверок API прежней.

## Что должен сохранять A3

- Для каждой проверки узла: `node_id`, UTC `observed_at`, `scope=node`,
  `success`, безопасный `error_code` и source session, если она известна.
- Для каждого снимка папки: `folder_id`, UTC `observed_at`, `success`,
  `actual_paused`, runtime state и безопасный код ошибки; не записывать секреты,
  физические пути и сырые ответы.
- Для каждой попытки B2: `status`, источник, `completed_at`, `created_at`,
  `verified_at`, `error_code`, `rule_version` и внутренние ID.
- Разрыв истории событий (`HistoryGap`) сохранять отдельным gap-маркером
  (`kind=gap`, `event_type=HistoryGap`), а не результатом проверки доступности.
  Если `system/status` успешно прочитан и разобран, node-snapshot остаётся
  успешным даже при таком разрыве; снимок папки определяется только своей
  фактической проверкой. Неуспешный snapshot создавать только для реально
  неуспешного соответствующего наблюдения; пропущенные значения не
  восстанавливать догадкой.

## Пример ручного расчёта

За период есть 3 попытки: `applied=1`, `failed=1`, `unknown=1`. Результат
`1/(1+1)=0.5`; неизвестная попытка отображается отдельно. Если есть 4 проверки
узла (`ok`, `ok`, `unreachable`, `auth_error`), результат `2/4=0.5`. Если
проверок нет, API возвращает `null`, а UI показывает «Нет данных».

## Реализация B4

Защищённый маршрут `GET /api/analytics/summary` возвращает итоги и строку для
каждой затронутой даты UTC. У периода длиной 31 сутки может быть 32 строки.
Пустой день сохраняется с нулевыми счётчиками и отношениями `null`. Фильтр
`node_id` ограничивает обе метрики внутренним UUID экземпляра.

PostgreSQL группирует завершённые попытки, ожидающие попытки и проверки узлов
одним SQL-запросом. Итоги и дневные строки строятся из одних и тех же счётчиков.
Экран показывает числители, знаменатели и отдельно состояния без подтверждения.

В общей сборке A добавляет `app.api.analytics.router` в список `routers`
фабрики `create_app`. Фабрика применяет общую авторизацию администратора.

## Проверки

На машине с Python 3.12, Node, Chromium и PostgreSQL запустите из корня
репозитория следующий сценарий с путём к установленным `initdb` и `pg_ctl`.

```sh
python tests/e2e/ui/check_postgres.py --bin-dir /path/to/postgresql/bin
```

Сценарий создаёт частный PostgreSQL, сверяет метрики с ручным расчётом T-13
и выполняет браузерную проверку через реальные HTTP API и SQL. В этом режиме
ответы Syncthing даёт тестовый адаптер.

Для прогона с двумя реальными Syncthing используйте отдельный демонстрационный
стенд A4, общую сборку с UI и маршрутом аналитики, работающий worker и чистую
папку без правил с начальным наблюдаемым состоянием «возобновлена».
Передайте Playwright loopback URL стенда в `B4_LIVE_URL`, внутренние UUID в
`B4_LIVE_NODE_ID` и `B4_LIVE_FOLDER_ID`, логин и пароль тестового администратора
в `B4_LIVE_LOGIN` и `B4_LIVE_PASSWORD`. Запускайте из каталога `frontend`.

```sh
npm run test:e2e
```

Сценарий создаёт правило в браузере, дожидается подтверждённой команды и
наблюдения паузы, проверяет историю и аналитику, затем удаляет созданное
правило и восстанавливает исходное состояние демонстрационной папки.
