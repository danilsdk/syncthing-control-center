# Переходы команд B0

Статус: реализуется в B2. Попытка команды подтверждает изменение конкретной
папки через адаптер Syncthing; HTTP-ответ сам по себе результатом не является.

## Состояния попытки

| Состояние | Смысл | Допустимые доказательства |
| --- | --- | --- |
| `pending` | намерение создано, команда ещё не отправлена или ожидает проверки | `created_at`, возможно `sent_at` |
| `applied` | свежая проверка подтвердила цель | `sent_at`, `verified_at`, `completed_at`, актуальная версия правила, `restart_required=false` |
| `failed` | определённый отказ или подтверждённое неприменение | `completed_at`, безопасный `error_code` |
| `unknown` | результат нельзя установить из-за связи, таймаута, рестарта или неполного наблюдения | `completed_at`, причина; не входит в знаменатель успеха |
| `cancelled` | намерение отменено до отправки | `completed_at`, причина; `sent_at` отсутствует |

Терминальная запись не изменяется. Новый повтор создаёт новую попытку и сначала
пересчитывает правило на текущий момент.

## Нормальный цикл

1. Получить свежую конфигурацию папки и текущее время через переданный `Clock`.
2. Рассчитать актуальное `desired_paused` по включённому правилу. Если правила
   нет или оно выключено, управление прекращается и новая команда не создаётся.
3. Если наблюдаемое значение уже совпадает с целью, сохранить наблюдение без
   успешной команды: это не должно завышать долю подтверждённых отправок.
4. Взять блокировку папки и повторно прочитать правило, его версию, состояние
   узла и наличие папки. При изменении/удалении правила, отключении узла или
   исчезновении папки создать `cancelled` с безопасной причиной.
5. Сохранить `pending` и зафиксировать `sent_at` отдельным commit **до** вызова
   внешнего API. До внешнего вызова используется только общий адаптер.
6. Вызвать `set_paused(folder_id, desired_paused)` через `syncthing_adapter`.
   Адаптер не скрывает повторные PATCH и не пишет ключ в журнал.
7. После ответа заново прочитать конфигурацию этой папки и
   `restart_required`. Проверять тот же источник и актуальную версию правила.
8. Только при совпадении `paused`, актуальной версии, той же source session и
   `restart_required=false` перевести запись в `applied`. Иначе использовать
   `failed` только при определённом неприменении, во всех недостаточных случаях
   — `unknown`.

## Повторы и изменения

- Таймаут, потеря связи, смена сессии Syncthing, ошибка чтения проверки и
  требуемый рестарт дают `unknown`; старая отправленная команда не проигрывается
  повторно.
- Повтор после `unknown` заново читает правило и состояние. Если цель успела
  примениться, сохраняется наблюдение без новой команды; если нет — создаётся
  новая попытка с новым snapshot.
- Изменение правила до отправки отменяет старое намерение. Изменение после
  отправки сохраняет фактический результат старой версии, но не подтверждает им
  новую версию: итог старой попытки `unknown` с причиной
  `rule_changed_after_send`, затем выполняется новый расчёт.
- Возвращение узла после недоступности начинает новый цикл с текущим UTC-моментом;
  пропущенное окно не воспроизводится задним числом.
- После перезапуска исполнителя незавершённая отправленная попытка становится
  `unknown` (`worker_interrupted`). Намерение без отправки пересчитывается.
- При активном правиле ручной `resume` отвергается конфликтом. Без активного
  правила ручная команда использует `source=manual`, `rule_id=null` и проходит
  тот же путь подтверждения.

## Минимальные поля истории

Попытка хранит внутренние ID узла и папки, источник `rule/manual`, snapshot
версии и параметров правила, цель, `created_at`, `sent_at`, `verified_at`,
`completed_at`, фактическое наблюдение, source session и безопасный код причины.
API-ключ, URL, физический путь и сырое тело Syncthing никогда не попадают в DTO,
лог или историю.
