# Репетиция защиты на изолированном стенде

Участники A и B могут повторить сценарий каждый на своей машине из checkout
`98ad53d6f474c0f9022d164324657a93d4564297`. На защите показываются расписание,
подтверждение команды, отказ одного узла и применение последней версии после
восстановления. Для испытания используются новые тома Compose и папка
`scc-a4-shared` только на узле `demo-a`.

## Подготовка

Понадобятся Python 3.12, запущенный Linux Docker Engine с Compose и Buildx,
а также два свободных loopback-порта 8000 и 8080. При занятых портах замените
их во флагах и используйте выбранный UI-порт в адресе браузера. Если имя проекта
уже занято, выберите новое имя вида `scc-a4-test-<суффикс>` (8–20 строчных
латинских букв или цифр) и подставьте его во все команды. При необходимости
передайте `--context desktop-linux` помощнику и тот же контекст Docker CLI.
Если команда `python` указывает на другую версию, используйте `python3.12`
на macOS/Linux или `py -3.12` на Windows. [Инструкция к Compose](../../../../deploy/compose/README.md)

```text
python scripts/dev_stack.py prepare --project scc-a4-test-b5defense --port 8000 --ui-port 8080
python scripts/dev_stack.py check --project scc-a4-test-b5defense
python scripts/dev_stack.py up --project scc-a4-test-b5defense
python scripts/dev_stack.py admin-create --project scc-a4-test-b5defense --login admin
python scripts/dev_stack.py status --project scc-a4-test-b5defense
```

Введите пароль интерактивно и оставьте один сервис `worker` запущенным.
Откройте `http://127.0.0.1:8080` и войдите. Зарегистрируйте два узла из уже
настроенных серверных подключений. Для нового проекта выполните следующий
фрагмент в консоли DevTools вкладки SCC после входа администратора. Браузер
передаст сессионную cookie и заголовок Origin, фрагмент добавит CSRF из
`/api/auth/me`. В консоль выводятся только названия зарегистрированных узлов.

```javascript
(async () => {
  if (location.protocol !== "http:" || location.hostname !== "127.0.0.1") {
    throw new Error("Откройте локальный стенд SCC.");
  }
  const sessionResponse = await fetch("/api/auth/me");
  if (!sessionResponse.ok) throw new Error("Сначала войдите в SCC.");
  const { csrf_token } = await sessionResponse.json();

  for (const ref of ["demo-a", "demo-b"]) {
    const response = await fetch("/api/nodes", {
      method: "POST",
      headers: { "Content-Type": "application/json", "X-CSRF-Token": csrf_token },
      body: JSON.stringify({ connection_ref: ref, display_name: ref }),
    });
    if (response.status !== 201) {
      throw new Error(`${ref}: HTTP ${response.status}. Проверьте узлы в панели.`);
    }
    console.log(ref);
  }
})();
```

Обновите страницу. В разделе «Папки» отфильтруйте узел `demo-a` и откройте
папку с ID `scc-a4-shared`. На исходном стенде в карточке есть свежее
наблюдение «Синхронизация разрешена» и нет действующего расписания. Дождитесь
этого состояния до первого изменения. Нажмите «На обзор», чтобы карточка
узла на «Обзоре» относилась к выбранной папке. Если повторяете показ на старых томах,
для чистого исходного состояния поднимите отдельный тестовый проект.

## Показ

Используйте `Europe/Moscow` и отметьте все семь дней. Возьмите за основу
текущее московское время. Задайте три окна: A — от +4 ч до +5 ч, B — от −1 ч
до +1 ч, C — от +6 ч до +7 ч. Часы вводятся по модулю 24. Благодаря выбору
всех дней эти окна работают и около полуночи. Если репетиция приблизится
к границе окна, пересчитайте значения. По умолчанию сбор идёт каждые 30 секунд,
проход правил — каждые 15 секунд. Между шагами можно перезагрузить страницу,
затем дождаться обновлённых данных и проверить время наблюдения.

| Шаг | Действие | Что проверить |
|---|---|---|
| 1 | В карточке папки нажмите «Создать правило». Сохраните включённое окно A (версия 1). | В «История → Команды» откройте строку для `demo-a` и этой папки. В записи версии 1 цель «Приостановить», результат «Подтверждено», наблюдаемая пауза включена и есть время проверки. |
| 2 | В правиле нажмите «Изменить» и сохраните окно B (версия 2). | В новой попытке по версии 2 подтверждено возобновление. В карточке папки появилась свежая фактическая пауза «Выключена». |
| 3 | Выполните команды остановки узла ниже. | В карточке папки дождитесь «Нет свежих данных». На «Обзоре» карточка `demo-a` показывает «Устаревшее наблюдение». По API у `demo-a` статус `unreachable`, у `demo-b` — `ok`. |
| 4 | Пока `demo-a` остановлен, сохраните окно A (версия 3). Дождитесь ещё одного цикла сбора и применения. Затем сохраните окно C (версия 4). | Обе версии сохраняются в SCC. В истории до запуска узла ноль отправок по версии 3. |
| 5 | Запустите тот же контейнер. | У узла появляется свежая успешная проверка. В истории новая попытка по версии 4 подтверждает паузу, а карточка папки показывает свежее «Приостановлена». В «История → Команды» отфильтруйте узел и папку. Откройте записи и проверьте версии. В журнале ноль отправок по версии 3. |
| 6 | В правиле выберите «Удалить» и подтвердите. В карточке папки нажмите «Возобновить». | Откройте отдельную ручную попытку и дождитесь подтверждённой паузы «Выключена». Вернитесь в карточку и проверьте свежее наблюдение и отсутствие активного правила. |

Для шага 3 получите ID только сервиса своего проекта. Команда должна вывести
ровно одну строку. Сверьте имя проекта, сервис и метку `io.scc.owner` с полем
`owner` в локальном `deploy/compose/runtime/scc-a4-test-b5defense/state.json`.
Приватные настройки и ключи для этого не требуются.

```text
docker ps --filter label=com.docker.compose.project=scc-a4-test-b5defense --filter label=com.docker.compose.service=syncthing-a --format "{{.ID}} {{.Names}}"
docker inspect --format "{{json .Config.Labels}}" ID_КОНТЕЙНЕРА
docker stop ID_КОНТЕЙНЕРА
```

Статусы обоих узлов можно сверить в консоли DevTools после входа.

```javascript
fetch("/api/nodes").then(async (response) => {
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const { items } = await response.json();
  console.table(items.map(({ display_name, api_status, last_checked_at }) =>
    ({ display_name, api_status, last_checked_at })));
});
```

Для шага 5 используйте `docker start ID_КОНТЕЙНЕРА`. Если показ прервётся на
отказе, сначала запустите остановленный контейнер. При завершении остановите
свой стенд с сохранением данных.

```text
python scripts/dev_stack.py down --project scc-a4-test-b5defense
```

## Показ аналитики

На принятом срезе `98ad53d` открытие «Аналитики» в штатном Compose приводит к
HTTP 404 для `GET /api/analytics/summary` даже в сессии администратора. Для
защиты на этом срезе используйте [формулы и расчёт T-13](automation.md#аналитика)
и [снимок отдельной проверки](evidence/06-analytics-preview.png). На снимке
видны 4 подтверждения из 4 команд и 14 успешных проверок из 16 по двум
узлам. Снимок получен после временного подключения маршрута к данным
репетиции. [Протокол отдельной проверки](evidence/analytics-preview.json)
После подключения маршрута в общей сборке повторите реальный сценарий и
откройте «Аналитика → Фильтры аналитики». Выберите период с попытками и узел
`demo-a`, покажите числители и знаменатели обеих метрик. Для периода без
проверок и попыток ожидается «Нет данных».
