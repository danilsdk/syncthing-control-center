Материал участника B / danilsdk для сборки отчёта A5. Описанная версия приложения — `98ad53d6f474c0f9022d164324657a93d4564297`. B реализовал расчёт расписаний и API правил (B1), исполнитель с подтверждением и историей попыток (B2), административный интерфейс (B3), показатели и пользовательские E2E-проверки (B4). B также подготовил harness разработки (H0). Интеграция с Syncthing, сбор наблюдений, схема БД и сборка Compose выполнены участником A.

## Расписание и применение

Правило управляет папкой конкретного экземпляра. В API папка адресуется внутренним UUID, а адаптер использует её Syncthing Folder ID в контексте выбранного узла. Для папки допускается одно включённое правило. Оно хранит дни недели ISO, локальные часы начала и конца, часовой пояс IANA, признак включения и версию. Изменения проверяют ожидаемую версию, чтобы правка из устаревшей формы не затёрла актуальные данные. [API правил](../../../../backend/app/api/rules.py), [описание B1](../../../design/b/scheduling.md)

В разрешённом окне `[начало, конец)` желаемое значение `paused=false`. Вне окна оно равно `true`. Окно пятницы 22:00–02:00 действует в субботу до 02:00, поскольку днём начала остаётся пятница. При выключенном или отсутствующем правиле целевое состояние равно `null`, фактическая пауза сохраняется до отдельной команды. При переходе на летнее время пропущенные локальные минуты отсутствуют в расчёте, а при переходе обратно каждое вхождение повторённой минуты оценивается по тому же окну. Отметки наблюдений и попыток хранятся в UTC. [Расчёт в B1](../../../../backend/app/scheduling/engine.py)

Один отдельный процесс удерживает блокировку PostgreSQL и последовательно запускает сбор наблюдений и проход исполнителя. В проходе B2 читает свежую конфигурацию папки через адаптер, рассчитывает цель по текущим часам и при расхождении записывает попытку с версией и снимком правила. Для `applied` требуются повторное чтение нужной папки в той же подтверждённой эпохе источника, совпадение `paused`, отсутствие требования перезапуска и актуальная версия правила при сохранении результата. HTTP-ответ фиксирует приём запроса. Результат применения виден в отдельной записи истории. [Код B2](../../../../backend/app/reconciliation/service.py), [стенд A4](../../../../deploy/compose/README.md)

| Ситуация | Что происходит |
|---|---|
| Узел недоступен до отправки | Коллектор записывает результат проверки узла. Исполнитель продолжает работу после восстановления связи со свежим наблюдением и актуальным правилом. |
| Ответ на запись потерян | Исполнитель пробует подтвердить исход повторным чтением. При недостатке доказательств попытка получает `unknown`. |
| Syncthing явно отклонил изменение или проверенное состояние расходится с целью | Попытка может завершиться как `failed` с кодом причины. |
| Правило изменилось после отправки | Результат старой версии отмечается `unknown` с `rule_changed_after_send`. Следующий проход пересчитывает цель. |
| После сбоя осталась незавершённая попытка правила | Намерение без отметки отправки становится `cancelled`. Попытка с отметкой отправки становится `unknown`. |
| Наблюдаемое `paused` уже равно цели | Исполнитель продолжает наблюдение. В истории остаются реальные попытки. |

[Решение о подтверждении](../../../../backend/app/reconciliation/decisions.py), [переходы и повторы B2](../../../design/b/reconciliation.md)

## Административный интерфейс

Администратор входит в панель, выбирает папку, задаёт окно и открывает историю команд. Карточка папки раздельно показывает фактическую паузу, свежесть наблюдения, состояние синхронизации и цель действующего расписания. Для каждой попытки доступны цель, результат, время отправки и проверки, объект и версия правила. События Syncthing открываются на отдельной вкладке истории. Интерфейс обращается к API SCC под сессией администратора. Ключи Syncthing хранятся на сервере. Имя, значок и закрепление папки относятся к настройкам браузера. ## Аналитика

Сводка принимает период `[from, to)` в UTC длиной до 31 суток. Дневные точки группируются по датам UTC. Фильтр узла ограничивает обе метрики, фильтр источника `rule` или `manual` — только попытки команд. [Запрос B4](../../../../backend/app/analytics/summary.py), [описание расчётов](../../../design/b/analytics.md)

| Показатель | Формула и состав выборки |
|---|---|
| Доля подтверждённых команд | `applied / (applied + failed)`. Завершённые попытки отбираются по `completed_at`. `unknown` и `cancelled` считаются отдельно, текущие `pending` отбираются по `created_at`. |
| Доля успешных проверок API | Число успешных проверок узлов, делённое на число выполненных проверок узлов. Наблюдения отбираются по `observed_at`. Пропуски запусков и снимки отдельных папок из выборки исключены. |

При нулевом знаменателе API возвращает `null`, а интерфейс показывает «Нет данных». На наборе T-13 одна подтверждённая и одна неуспешная попытки дают 1/2, две успешные проверки из четырёх дают 2/4. В наборе также присутствуют неизвестная, отменённая и ожидающая попытки. PostgreSQL-проверки охватывают день без наблюдений, фильтры и случай, когда период в 31 сутки затрагивает 32 даты UTC. 26.11.2026 на этой версии прошли все три теста T-13. [Входные данные и проверки](../../../../tests/integration/analytics/test_summary_postgres.py)

**Состояние общей сборки.** Модуль аналитики и экран приняты в B4. В штатном Compose на `98ad53d` запрос `GET /api/analytics/summary` после входа вернул HTTP 404. Маршрут отсутствует в списке роутеров стандартной фабрики A. В отдельной проверке B5 маршрут временно подключили через `create_app(routers=[...])` к данным той же репетиции. За период прогона подтверждены 4 из 4 команд (100 %) и 14 из 16 проверок API обоих узлов (87,5 %). Для пустого периода обе карточки показали «Нет данных». Для демонстрации экрана на общем стенде требуется интеграционная правка A и новый живой прогон. ## Пример разработки с coding agent

В B4 агент добавил браузерный тест с созданием правила, сверкой попытки в истории и восстановлением тестовой папки. Независимый review на PR #21 выявил риски очистки при сбое и потере ответа на создание правила. В повторной проверке обнаружился ещё один сценарий: сразу после `202` на ручное возобновление реестр мог вернуть `actual_paused=false`, прочитанное до запроса. Тест принимал старое наблюдение за результат новой попытки.

Тест теперь берёт UUID из ответа `202`, опрашивает именно эту попытку и проверяет терминальный результат. Для `applied` требуется наблюдаемое `false` и время подтверждения. Для `cancelled/already_resumed` исполнитель сам наблюдал уже возобновлённую папку. В обоих случаях тест дополнительно проверяет свежую запись реестра. Исправление проверили в отдельном ARM64 Compose с реальным PostgreSQL и двумя Syncthing. После сценария сравнили четыре конфигурации демонстрационных папок с исходными. Принятое изменение сохранилось в PR #21.
